# Agent Operating Instructions

## Consuming-project bootstrap

When PCM is supplied alongside an existing project repository, treat PCM as an executable control system, not reference guidance.

1. Do not invent an alternative workflow in conversation.
2. Before an accepted brief exists, orientation only is permitted.
3. Once an accepted brief exists, run the PCM `instantiate` front door against the target Git repository before project planning or implementation.
4. Instantiation must record the exact PCM methodology commit/tree, target-repository starting commit/tree, accepted-brief identity/hash, and any canonical native project authority present at the target source commit.
5. Never overwrite, rename, or repurpose pre-existing native project authority during bootstrap. PCM-generated project-specific authority lives under `.pcm/project/`; draft only `PROJECT_OBJECTIVE.md`, `REQUIREMENTS.md`, and `EXEC_PLAN.md` there while `template_mode=true`. The installed `.pcm/GUARDRAILS.md` and `.pcm/AGENTS.md` are frozen methodology authority and must not be replaced by project-local Guardrails or Agents files.
6. Ordinary project execution is prohibited until `finalize-instantiation` succeeds under `PROGRAMME_OWNER` authority.
7. After finalisation, derive every executable transition from `projectctl` and committed Git state.
8. If PCM cannot represent a required project rule, stop `BLOCKED`. Do not invent a parallel process.

In the PCM methodology repository, the controller path is `scripts/projectctl.py`, task/delegation state is under `control/`, and the PCM execution plan is root `EXEC_PLAN.md`. In an instantiated consuming project, those paths are `.pcm/projectctl.py`, `.pcm/control/`, and `.pcm/project/EXEC_PLAN.md`. Apply the consuming project's applicable native authority together with its namespaced PCM project authority; do not use methodology-source distribution state as the consuming project's execution plan.

## Role-specific entry and re-entry

First establish repository identity and the operational role explicitly appointed by the user in the current thread. Read `GUARDRAILS.md` in full, read this file and every applicable nested `AGENTS.md` / `AGENTS.override.md`, run the applicable controller `check`, and inspect the primary evidence required for the exact claim or action. Repository state, `ready`, delegation, generated context, re-entry, and session operations do not appoint a role or change that appointment.

Use the entry path for the appointed role:

- **Bootstrap PM:** follow the consuming-project bootstrap above. Inspect the accepted brief and real repository, use the existing `instantiate` front door, draft namespaced project authority only within authorised planning/governance scope while `template_mode=true`, and obtain programme-owner finalisation. `ready`, worker `context`, and execution sessions are not ordinary bootstrap steps before finalisation.
- **PM/orchestrator after finalisation:** run `check` and `ready`, then inspect the applicable committed task metadata, plan block, and delegation state. Route the currently identified responsibility. Do not confuse execution readiness with appointment: when a downstream worker responsibility is already defined by the finalised task graph/delegation, the PM may also prepare and issue its bounded handoff prospectively so that worker can initialise and wait for its dependencies. The PM does not need the user to return after each predecessor merely to obtain a handoff whose task identity, role and bounds are already committed. When a bounded worker responsibility has a declared independent-review successor, ensure an independent reviewer is appointed without creating a redundant chat thread. If an already-independent test/proof thread is intended to perform that later review and did not author the implementation candidate, retain or reappoint that thread as the reviewer; otherwise appoint/dispatch the worker and reviewer together. The reviewer is allowed to initialise and wait before its leaf is executable. Do not take the worker `context` → execute path merely because the leaf actor class is `AUTONOMOUS`. After reviewer `PASS`, resume PM routing for the next governed transition. Do not interpose the PM between reviewer and worker for an in-envelope `REPAIR`. Authorised governance maintenance remains permitted within its existing scope and admission rules.
- **Assigned author/worker:** establish repository identity and the appointed task, run `check`, and inspect `ready`. If the specifically assigned `AUTONOMOUS` responsibility is not yet ready, report that setup is complete and wait for repository state containing its admitted dependencies; do not execute another ready leaf, request/use `context` for the future leaf, or treat the prospective handoff as execution authority. Once that exact assigned responsibility is lawful/ready, create or switch to a non-acceptance work branch and admit that branch transition before requesting `context`; autonomous execution must not begin on the configured acceptance branch. Then run `context` and execute only its bounded scope and stop condition, following the existing execution-window/session rules. On an in-envelope independent-review `REPAIR`, receive the finding directly from the reviewer. If accepted history requires a new stable repair ID, use the existing same-actor bounded-refinement mechanism; this does not require PM routing. Return changed candidate bytes for a fresh review packet/result. Stop and route to PM/programme owner if the correction cannot stay inside the admitted envelope.
- **Independent reviewer:** the reviewer may be newly appointed alongside the worker or may be the already-independent thread that previously performed the governing test/proof responsibility, provided it did not author the implementation candidate and is currently appointed to the review role. On review appointment/re-entry, establish repository identity, read applicable authority, run `check`, and wait if no lawful review packet exists yet. Once the review leaf is lawful and the exact candidate/current packet is supplied, use the existing reviewer session/validation path. A `REPAIR` is returned directly to the owning worker; `PASS` returns to the PM/orchestrator; inability to establish a lawful in-envelope result is `BLOCKED` and returns to governance. Fresh review of changed candidate bytes means a new packet/result bound to those bytes; it does not by itself require a different reviewer chat thread from the already-independent reviewer. A refusal of worker `context` at an `INDEPENDENT_REVIEW` leaf is expected and is not permission to bypass review.

Generated context is a bounded projection for execution convenience. It is never authority and must fail closed if its source fingerprints do not match current governing files. Do not use `checkpoint` to erase a failed `check`. In normal LCR-mode field use, stage the intended transition, run `checkpoint` with the explicit admission flag(s) for that transition, then commit the substantive change and generated LCR together once. Do not create a second LCR-only commit merely to mirror a transition already being committed.

Do not edit the applicable generated LCR (`control/lcr.json` in the methodology repository or `.pcm/control/lcr.json` in a consuming project) to select work, alter the next transition, or resolve uncertainty. Active work is derived from committed task state; unresolved epistemic state belongs in `control/claims.json` in the methodology repository or `.pcm/control/claims.json` in a consuming project. When an assigned worker faces more than one ready task, commit exactly one lawful task as `in_progress` through the existing selection/admission mechanism before requesting context; do not infer a unique task or hand-edit the LCR.

The applicable delegation file (`control/delegation.json` or `.pcm/control/delegation.json`) is governing authority for the actor class of every executable leaf, not for the operational role of the current thread. `AUTONOMOUS` identifies the class of responsibility that an assigned worker may execute; it does not turn an appointed PM/orchestrator into that worker. If the active responsibility is `INDEPENDENT_REVIEW`, stop author execution and hand the existing review packet to the already-appointed independent reviewer context, including an eligible earlier test/proof thread, or appoint a new independent reviewer if none already exists. If it is `PROGRAMME_OWNER`, stop for the programme owner. Do not use checkpointing, context, or session restart to weaken either boundary.

Use stable execution IDs, never Markdown line numbers, for durable task/dependency/recovery references. Preserve the `ID — human label` form so programme owners can review plans without decoding IDs.

## PCM V5 field-use operating rule

The methodology repository is a V5 field-use source distribution. Its root `EXEC_PLAN.md` and `control/tasks.json` are intentionally dormant source-state records; they are not a methodology-development programme and are not a consuming project's execution plan.

The canonical methodology branch is `main`. The exact current committed V5 `main` commit/tree is the methodology identity used by `instantiate`. No predecessor branch or methodology-development history is required authority for field use.

## Verification

Do not claim reviewed, fixed, complete, passing, clean, accepted, or current without corresponding command/file/diff/evidence output.
