## Prospective proof-design limitations

The orthogonal K06 positive sample is mathematically sound but does not distinguish a correct joint fit from three separate univariate fits, because orthogonality makes both return the same slopes. Likewise a zero residual alone has limited discriminatory power. This is a limitation to address when selecting the future authorised success/refusal data and physical case budget, not permission to add or run cases now. The historical exact two-case allocation is not automatically enlarged by every row or recipe here; the new plan must explicitly reconcile family sharing, per-D propositions and the governing budget.

Current controlled `_relative_market_return.py:43–115` hard-binds the existing D076 request/context/as-of and validates actual predecessor occurrences. Generic legacy `_stage1.py` contains K06/D091/D142/D144 branches, but their presence is not an admitted controlled M02 implementation: for example its D142 branch uses a depth-OR-spread onset and event timestamps, whereas the tentative V1 uses joint onset and declared synthetic receipt time. Reusing that path without an exact versioned contract would silently change the proposal. The public native API has snapshot/history and typed book/source lineage seams, but those types do not independently create simultaneous SMART/direct fixtures or an admitted new matched-comparison result. No existing accepted code should be changed based only on this observation. Plan contract work first and establish the appropriate owning surface explicitly.
