## B. What lawful creation and retirement actually mean

`docs/architecture/EXTENSION_AND_RETIREMENT_RULES.md` AK-EXT-001/AK-LIFE-001 says to allocate the **next unused** M ID only after valid authority, establish a bounded owner and its exclusions, interfaces, state/write/read/time responsibilities, lawful declared dependencies, typed public seam and exact proof. `docs/architecture/IMPLEMENTATION_AUTHORITY_INGRESS.md` AK-INGRESS-001–005 requires one **externally accepted implementation-ready brief bound by exact raw-byte SHA-256**, an acceptance reference, and lawful projections. A **new** `create` projection specifies category `M` and a concise responsibility name; **it may not specify the numeric ID**. `modify` is for an existing current ID. `src/nvda_desk/architecture/allocation.py` obtains consumed IDs from current registry, retired IDs and durable implementation allocations; `identifiers.py:next_identifier` chooses max-used-plus-one; `resolve_candidate_identifiers` also accounts for earlier candidates in the same ingress request. That mechanical candidate resolution is **non-durable**, not registration and not permission to implement.

**Conditional consequence:** With current M consumption only `{M00,M01}`, a future first admissible M `create` would resolve candidate `M02`; 31 consecutive ordered creates from the same unchanged state would nominally produce M02–M32. This is an **inference from code and presently registered inputs**, not a run, reservation or approved sequence. A changed consumption/order/scope may change the outcome. If lawful resolution does not produce the owner's desired working name, **stop and escalate**; do not hand-pick a number, silently renumber a group, falsify allocations or introduce placeholder registration just to fix labels.

`EXTENSION_AND_RETIREMENT_RULES.md` distinguishes `deprecated` (no new composition, retirement path needed) and `retired` (absent from active composition, identity permanently reserved). `src/nvda_desk/architecture/registry.py` enforces current registered/post-reset retired lifecycle endpoints, no self-lineage and reciprocal relationships between currently registered endpoints. **M01 has no present successor relationship recorded.** `DO_NOT_CARRY_FORWARD` is solely a future *target active-tree* disposition preserving ordinary Git history; it does **not** retire a module or populate `retired_ids`. Retirement needs an independent explicit programme authority. No lifecycle change was made.

### Concrete stored-result incompatibility risk

The present D occurrence ID contains no M module-owner component. If identical input IDs and versions are used by an old M01 calculation and a proposed successor, the occurrence identity construction can yield the same string even when the recognised state owner and persistence boundary are different. Conversely, changing versions or the dependency/input selection changes the hash and may break old references. These are **mechanistic risks supported by the inspected implementation**, not an assertion that an actual collision or production migration exists. The authoritative future decision must explain historical lookups, unchanged accepted D meaning, record authorship and lineage, rather than assuming the new owner can claim old durable facts.
