# Recovery snapshot contexts — independent finding and bounded correction

The independent B reviewer found an ISOLATED snapshot-context defect in the first Worker recovery procedure. The earlier procedure preserved 2,281 rows' object identities and recreated/ref-read each row sequentially, but grouped restore bundles only by outer inventory filename. CURRENT_REF_MANIFEST.json contains multiple nested historical snapshots: exported_refs and remote_snapshot bind execution/accepted-r1-20261030 to363923d..., while retained_worker_e19_snapshot binds the same literal name to e19c2d.... Its final per-inventory bundle therefore retained e19c2d under that name; two363923d rows were not simultaneously present under their literal name after final bundle restore.

The original published-successor restoration of all779 exported refs was separately and correctly verified; no object loss or source-history defect was found. All170 distinct required object tips remain available. The earlier blanket per-inventory all-row bundle-restoration claim is narrowed to sequential historical recreation; it is superseded for current restoration by the context-specific procedure and evidence here. Original logs and historical acceptances stay unchanged.

restore_snapshot_contexts.py retains each governing ref-map's JSON path as its snapshot context. Each context is represented under an explicit transport namespace in one self-contained full-history bundle. A fresh empty repository verifies and fetches that bundle, fsck checks the complete object store and compares the final namespaced ref inventory. Isolated per-context views then recreate the literal names, read EVERY name after the complete snapshot has been installed, and fsck against the freshly restored shared object store. The views explicitly share that object store; they are not described as separately self-contained bundles. Only the pre-existing documented work/work/* collision uses refs/preservation/local-bootstrap-work.

This preserves every literal ref/tip at its own checkpoint without confusing different historical snapshots, silently overwriting main or renaming arbitrary required refs. The exact source map, JSON path, namespace mapping, final readback and bundle hash are retained in REQUIRED_REF_RESULTS_CURRENT.json and SNAPSHOT_CONTEXT_RESTORE.json. Raw commands/results are losslessly recorded in SNAPSHOT_CONTEXT_COMMANDS.json.gz. No historical inventory or original receiver report is rewritten.

The new full bundle is a reproducible transport for these contexts, not the original base/archive bytes. The owner-approved remote-checkpoint method remains contingent on the actual required source-ref/asset set; current governance installation does not assert full original historical-binary recovery or product admission.
