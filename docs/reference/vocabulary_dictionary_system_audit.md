## Canonical vocabulary artefact

The canonical dictionary is the checked-in JSON document:

- `docs/vocabulary/2026-03-25_CANONICAL_DESK_COGNITION_VOCABULARY.json`

The repo-level vocabulary README defines this folder as the place that governs canonical repo language after architecture is pinned. It states that the purpose is to keep one term meaning one thing, keep aliases explicit, stop stale labels drifting back in, and preserve distinctions between primitives, derived features, stage labels, family labels, setup variants, execution expressions, and workflow-routing concepts. It also states that this layer is **not** a blind merge target, **not** a runtime redesign surface, and **not** a free-form glossary detached from typed contracts. Evidence: `docs/vocabulary/README.md:3-16`.

## Governing documents

### 1. Vocabulary governance overview
- `docs/vocabulary/README.md`

This file identifies the authoritative artefacts for the vocabulary system: the workflow document, canonical JSON file, alignment note, schema file, and generator. Evidence: `docs/vocabulary/README.md:18-24`.

### 2. Consolidation workflow
- `docs/vocabulary/CONSOLIDATION_WORKFLOW.md`

This file defines the allowed flow:

1. harvest candidate terms from current repo surfaces and bounded planning artefacts;
2. reconcile them against the canonical vocabulary file;
3. classify each candidate as exactly one of:
   - `enrich_existing`
   - `add_new`
   - `alias_only`
   - `quarantine`
4. regenerate the canonical vocabulary file from current live architecture;
5. run enforcement tests.

It also sets guardrails:

- do not blindly merge stale harvested payloads;
- do not let one label point to two different contract surfaces;
- do not treat compatibility labels as canonical runtime truth;
- do not let a new family, setup variant, execution expression, horizon, or workflow-routing concept land without a canonical vocabulary entry.

Evidence: `docs/vocabulary/CONSOLIDATION_WORKFLOW.md:3-23`.

### 3. Feeder area
- `data/vocabulary/feeder/README.md`

This file makes the feeder area non-canonical. Harvested terms and reconciliation drafts are only candidate material until they are reconciled into the canonical vocabulary file and pass enforcement tests. Evidence: `data/vocabulary/feeder/README.md:1-6`.

## Schema inventory

The schema contract for the vocabulary system is:

- `src/nvda_desk/schemas/vocabulary.py`

### Enumerations

The file defines two controlled enumerations:

- `VocabularyCategory`
  - `stage`
  - `playbook_family`
  - `setup_variant`
  - `execution_expression`
  - `horizon`
  - `compatibility_surface`
  - `data_classification`
  - `workflow`
- `RawDerivedTag`
  - `raw`
  - `derived`
  - `not_applicable`

Evidence: `src/nvda_desk/schemas/vocabulary.py:18-32`.

### `VocabularyEntry`

Each governed vocabulary item is represented by `VocabularyEntry`, with these fields:

- `canonical_slug`
- `canonical_label`
- `category`
- `stage_owner`
- `family`
- `setup_variant`
- `execution_expression`
- `horizon`
- `raw_or_derived`
- `maps_to_contract`
- `allowed_aliases`
- `disallowed_phrases`
- `notes`

The model is closed with `extra="forbid"`, so undeclared fields are rejected. Evidence: `src/nvda_desk/schemas/vocabulary.py:35-52`.

### `VocabularyDocument`

The canonical JSON document is represented by `VocabularyDocument`, with these top-level fields:

- `schema_version`
- `registry_version`
- `notes`
- `entries`

The model is also closed with `extra="forbid"`. Evidence: `src/nvda_desk/schemas/vocabulary.py:55-63`.

### Built-in validation rules

The schema file enforces:

- every `canonical_slug` must be unique;
- every `canonical_label` must be unique;
- a canonical label cannot also appear in its own alias list;
- an alias cannot be reused by a different vocabulary entry;
- a canonical slug cannot also appear in its own alias list.

Evidence: `src/nvda_desk/schemas/vocabulary.py:65-85`.

### Utility methods

The schema file also provides:

- `entry_index()` to build a slug-indexed lookup;
- `from_json_text()` and `from_json_path()` to load the JSON document;
- `to_json_text()` to serialise the validated document.

Evidence: `src/nvda_desk/schemas/vocabulary.py:87-104`.

## Generator

The canonical JSON is generated by:

- `scripts/build_canonical_vocabulary.py`

The script describes itself as building the canonical desk vocabulary document and imports the vocabulary schema contracts. It writes to:

- `docs/vocabulary/2026-03-25_CANONICAL_DESK_COGNITION_VOCABULARY.json`

Evidence: `scripts/build_canonical_vocabulary.py:1-25`.

The generator constructs a `VocabularyDocument` from governed entries and live repo architecture surfaces, then serialises that document back to the committed JSON path. Evidence: `scripts/build_canonical_vocabulary.py:25`, `scripts/build_canonical_vocabulary.py:882-899`.

Operationally, this means the canonical JSON is intended to be **generator-owned**, not manually drifted.

## What the system does do

### 1. It provides one canonical governed vocabulary registry

The repo has a single checked-in canonical JSON file for governed vocabulary. The README and workflow point to that file as the canonical artefact. Evidence: `docs/vocabulary/README.md:18-24`, `docs/vocabulary/CONSOLIDATION_WORKFLOW.md:7-15`.

### 2. It types vocabulary entries

Each entry is not just prose. It is tied to structured fields such as category, owner, contract mapping, alias list, disallowed phrase list, and notes. Evidence: `src/nvda_desk/schemas/vocabulary.py:35-52`.

### 3. It prevents exact collisions

The schema prevents duplicate slugs, duplicate labels, and alias reuse across entries. Evidence: `src/nvda_desk/schemas/vocabulary.py:65-85`.

### 4. It allows bounded alias policy

The system supports explicit `allowed_aliases` and `disallowed_phrases` for each governed entry. Evidence: `src/nvda_desk/schemas/vocabulary.py:49-52`.

### 5. It keeps the committed JSON tied to the generator

The committed JSON is meant to match the generator output exactly, and there is a test that enforces that. Evidence: `tests/test_gate60_state_policy_ontology.py:137-145`.

### 6. It supports whole-repo literal hygiene checks for selected phrases

The Gate 179 test scans the whole repo for specific watched aliases and disallowed phrases and ensures they only occur in bounded approved files. Evidence: `tests/test_gate179_repo_wide_vocabulary_hygiene.py:98-157`.

### 7. It supports boundary-specific vocabulary enforcement where the repo has added dedicated tests

The Gate 242 test proves that this vocabulary system can be extended with dedicated boundary-specific checks for a particular lane or concept family. Evidence: `tests/test_gate242_options_flow_history_lane_vocabulary_and_boundary.py:13-45`.

## What the system does not do

### 1. It does not do general semantic synonym detection

There is no schema rule or test in this system that reasons semantically about whether a newly proposed label is conceptually too similar to an existing label.

What exists is exact-identity and exact-phrase enforcement:

- exact uniqueness for slug and label;
- explicit alias lists;
- explicit disallowed phrase lists;
- literal whole-repo text scans for selected watched phrases.

Evidence: `src/nvda_desk/schemas/vocabulary.py:65-85`, `tests/test_gate179_repo_wide_vocabulary_hygiene.py:98-157`.

### 2. It does not automatically decide whether a candidate term should be reused, aliased, added, or quarantined

That decision is part of the workflow, not part of automated reasoning inside the vocabulary schema. The workflow says the candidate must be classified as one of `enrich_existing`, `add_new`, `alias_only`, or `quarantine`, but the classification itself is a governed reconciliation step. Evidence: `docs/vocabulary/CONSOLIDATION_WORKFLOW.md:7-15`.

### 3. It does not accept feeder content directly

The feeder area is explicitly non-canonical until reconciliation into the canonical JSON and passing enforcement tests. Evidence: `data/vocabulary/feeder/README.md:1-6`.

### 4. It does not redesign runtime architecture

The README and schema docstring both state that the vocabulary layer records and validates vocabulary after the runtime architecture is pinned; it does not redesign runtime behaviour. Evidence: `docs/vocabulary/README.md:3-16`, `src/nvda_desk/schemas/vocabulary.py:1-6`.

## Required upstream behaviour

The vocabulary layer should remain narrow.

If another code path, tool, or LLM-driven workflow believes it needs a new durable term, that upstream component should **not** invent and persist the term directly into code, docs, or durable planning surfaces.

Instead, upstream should do this:

1. read the canonical vocabulary file;
2. check whether an existing governed term already covers the concept;
3. classify the candidate as exactly one of:
   - `enrich_existing`
   - `add_new`
   - `alias_only`
   - `quarantine`
4. if the candidate is genuinely admitted, update the generator and any bounded alias/disallowed-phrase policy required by the admission;
5. regenerate the canonical JSON;
6. run the vocabulary enforcement tests;
7. only then allow the new term to persist as durable repo language.

That upstream discipline is the missing semantic check. The vocabulary system itself is the canonical registry and exact-string enforcement layer. Evidence for the required workflow basis: `docs/vocabulary/CONSOLIDATION_WORKFLOW.md:3-23`.

## How new terms are accepted

A new term is **not** accepted merely because someone typed it into a file.

Under the current repo design, acceptance requires all of the following:

1. the candidate term is reconciled against the canonical vocabulary file;
2. the candidate is classified through the workflow;
3. the canonical generator and governed entry set are updated where required;
4. the canonical JSON is regenerated;
5. the enforcement tests pass.

In practical terms:

- if the term already exists, the correct outcome is reuse or bounded aliasing, not a duplicate label;
- if the term is only a compatibility or convenience phrase, it may become an alias rather than a new canonical entry;
- if the term is not lawful for canonical adoption, it should be quarantined;
- if it is a genuinely new governed term, it should be added through the generator-backed canonical path, then proven by tests.

This is why the workflow is a **feeder process only** and why the feeder area is explicitly non-canonical until reconciliation and test pass. Evidence: `docs/vocabulary/CONSOLIDATION_WORKFLOW.md:3-23`, `data/vocabulary/feeder/README.md:1-6`.

## Clean operating interpretation

The current vocabulary system is best understood as four layers:

1. **governance documents** — define the rules and allowed flow;
2. **schema contracts** — define the allowed structure and exact uniqueness rules;
3. **generator** — produces the canonical checked-in JSON from governed repo surfaces;
4. **tests** — prove generator parity and selected phrase/boundary hygiene.

The semantic judgement about whether a candidate durable term is truly new must be handled **upstream** before the canonical registry is changed.

## Bottom line

The vocabulary dictionary system on `main` is a governed, generator-backed, exact-string enforcement system.

It is designed to:

- keep one canonical label per governed concept;
- keep aliases explicit;
- prevent exact collisions;
- mark selected phrases as disallowed;
- regenerate the canonical JSON from governed sources;
- enforce parity and selected whole-repo hygiene through tests.

It is **not** designed to perform general semantic synonym reasoning by itself. That judgement must be performed upstream, and only reconciled, generator-backed, test-passing results should become durable vocabulary.
