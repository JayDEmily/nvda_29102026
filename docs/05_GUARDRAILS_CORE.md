# 05_GUARDRAILS_CORE

All repo paths in the numbered control stack are repo-root-relative.


## Core guardrail rule

Convenience is not authority.

A change is invalid if it makes the repo easier to operate, easier to explain, or easier to code while breaking the declared structure, boundaries, or meanings defined by the live control documents.

## Structural guardrails

The following moves are prohibited unless explicitly and lawfully revised:

- collapsing real-data admission and runtime preparation into untracked side effects
- erasing the financial-calendar reference and projection step as a governed runtime step
- collapsing the six-stage serial desk-cognition spine into an unstructured path
- erasing a stage boundary inside the serial desk-cognition spine
- merging the serial desk-cognition spine and the independent parallel risk lane into one runtime path
- turning the independent parallel risk lane into part of serial candidate formation
- bypassing the downstream pre-deployment gate before capital deployment authority acts
- turning capital deployment authority into part of serial candidate formation
- turning capital deployment authority into general portfolio management
- turning capital deployment authority into close-position logic
- collapsing downstream opening, execution, inventory, and close architecture into one blended function with candidate formation or capital deployment authority
- collapsing candidate formation, environmental assessment, downstream pre-deployment blocking, and fresh-capital decision into one blended function
- allowing a compatibility surface to replace a more truthful preserved surface

## Authority guardrails

The following moves are prohibited:

- bypassing the live control stack through chat interpretation
- treating retained evidence as live authority
- using a lower-priority surface to weaken or reinterpret a higher-priority surface
- widening scope by implication
- letting a routing document act as a doctrine document
- letting a doctrine document act as a router

## Vocabulary guardrails

The following moves are prohibited:

- introducing a new durable term where an established term already exists for the same meaning
- using near-synonyms that blur a domain boundary or technical boundary
- renaming a concept in one live control surface while leaving the related live control surfaces unreconciled
- using casual wording that weakens a bounded role, boundary, or prohibition

Vocabulary is controlled to stop meaning drift.

## Explanation guardrails

The following moves are prohibited:

- presenting candidate formation, environmental assessment, downstream pre-deployment blocking, and fresh-capital decision as if they were the same result
- hiding which part of the system produced which result
- requiring guesswork to reconstruct what happened
- collapsing different outputs into one blended explanation for convenience

The repo is not acceptable if a reviewer cannot tell, in plain language, what each major part concluded.

## False-closeout guardrail

The following moves are prohibited:

- claiming work is done when known contradictions remain unreconciled
- claiming work is done when required control surfaces disagree about the current state
- claiming work is done when the stated repo truth is not the actual repo truth

A clean narrative does not make incorrect work complete.

## Native Architecture Blueprint boundary

Within native code-structure architecture scope, this document must be read with `docs/11_NATIVE_ARCHITECTURE_BLUEPRINT_CORE.md`.

`docs/11_NATIVE_ARCHITECTURE_BLUEPRINT_CORE.md` owns target package placement, component form, seams, ownership, persistence, test-family mapping, reservations, module allocation, and traceability for native code-structure architecture.

It does not override the authority hierarchy defined by `docs/01_NORMATIVE_CORE.md`.

All durable terms used by live control documents must be governed by `docs/vocabulary/vocabulary_registry.md` or lawfully admitted by the vocabulary process before they become canonical language.
