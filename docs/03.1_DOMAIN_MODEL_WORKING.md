# 03.1_DOMAIN_MODEL_WORKING

All repo paths in the numbered control stack are repo-root-relative.

## Status

This working overlay contains an admitted alpha-stage expansion of `docs/03_DOMAIN_MODEL_CORE.md` for raw-input meaning, identifier ownership, typed input extensibility, and the separation of source truth from packet carriage.

The core domain boundaries remain binding. This overlay does not make input admission part of candidate formation, capital deployment, execution, inventory, close, or review authority.

## 3.1 Raw-input domain meaning

A raw input is evidence presented to the system before runtime preparation and domain cognition. In this overlay, `raw input` is descriptive shorthand for the external payloads and raw/captured/reference material already governed by `docs/03`, `docs/04`, and `docs/11`; it does not create a new architecture surface or owner.

Admitting a raw input means establishing what source material was received, what it claims to represent, which contract applies, whether it is valid enough to enter the governed path, and how later material can trace back to it.

Admission does not mean that the input is true in every substantive respect. It means that source identity, source semantics, contract, temporal truth, validation outcome, and lineage are explicit enough for later governed interpretation.

A raw-input boundary must not make candidate, risk, capital, broker, exit, close, or review decisions.

## 3.2 Required raw-input identity and contract facts

Every admitted raw-input carrier must preserve, as applicable to its source contract:

1. the input family or contract identity;
2. the contract or schema version;
3. the upstream provider and acquisition channel;
4. any source-supplied object, event, observation, record, or artefact identifier;
5. the repository-owned identity of the captured payload, file, response, or receipt;
6. source observation time and repository process time under `docs/04.1_TECHNICAL_ARCHITECTURE_WORKING.md`;
7. immutable lineage or fingerprint material sufficient to identify the original captured evidence;
8. the validation outcome and any admitted limitations;
9. the exact typed payload contract used for downstream preparation.

The exact required facts may differ by input family. The applicable typed contract must declare which facts are mandatory, unavailable by source design, optional, or not applicable.

For every identifier it carries, the contract must state the originating owner, scope or namespace, uniqueness rule, stability rule, generation rule, and lawful absence rule. It must not imply global uniqueness where the owning source guarantees uniqueness only within a narrower scope.

A source that lawfully supplies only date-level temporal truth, no source-issued record identifier, or another bounded limitation must preserve that limitation explicitly. The system must not invent finer precision or pretend that a repository-owned identifier was issued by the source.

## 3.3 Identifier ownership and propagation law

Each material identifier has one originating owner and one bounded meaning.

The upstream provider owns any identifier that the provider supplies for its own object, event, observation, record, or artefact. An ingress adapter preserves that value and its source context. It must not rewrite, replace, or manufacture a provider-issued identity.

The repository ingress or raw-capture authority may create a repository-owned capture, payload, file, response, or receipt identity when it admits source material. That identifier names the repository's captured evidence. It must remain distinguishable from any source-supplied identifier.

A domain authority may originate an identifier only for the domain object, decision, state transition, or receipt that it owns.

DMPV3 `id`, `traceid`, `runid`, `scenarioid`, and packet-lineage fields identify packet carriage, execution context, or declared dependencies. They do not become substitutes for a missing source, domain, decision, position, execution, or state identifier.

Downstream components may propagate an upstream identifier through lawful carriers. They must not silently reassign its meaning, replace it with a local convenience value, or generate a plausible substitute when the required owner has not supplied one.

Where an applicable contract requires an identifier or lineage fact and the originating owner has not supplied it, the input or downstream transition must fail closed, remain explicitly non-admitted, or stand down. A correlation identifier, trace identifier, hash, timestamp, file name, array position, or randomly generated value must not be presented as the missing authoritative identity.

## 3.4 Typed extensibility at the input boundary

The input boundary must combine a stable common set of admission facts with input-family-specific typed payload contracts.

A new provider or input family must ordinarily be introduced through:

- one explicit external adapter or source reader;
- one typed carrier and versioned payload contract;
- one controlled registration or configuration entry;
- source-specific validation and mapping;
- contract, rejection, lineage, and substitution tests added later under Gate C.

Adding or replacing one input family must not ordinarily require changes to unrelated domain stages, playbooks, capital authority, inventory, close behaviour, or other input adapters.

Provider-specific field names, transport protocols, omissions, and conventions must be translated at the external boundary. They must not leak into the core domain as hidden assumptions.

A generic dictionary, unvalidated payload, payload-shape guess, or nearest-known-schema coercion is not an admitted typed boundary contract.

An unknown or unsupported input family must remain outside governed runtime preparation until a lawful contract and owner are admitted. The system must not reinterpret it as a familiar family merely to continue processing.

## 3.5 Source truth, prepared truth, and packet carriage remain separate

Raw source evidence, prepared runtime truth, and packet carriage are related but distinct domain meanings.

The ingress and raw-capture boundary preserves source evidence and its limitations.

Runtime preparation converts admitted source/reference material into runtime-ready typed inputs without changing the historical identity of the source evidence.

DMPV3 carries bounded outputs between modules. Its outer envelope standardises carriage; it does not originate or replace upstream source truth.

A later prepared field may have a new derived meaning and its own lawful owner. Its lineage must still identify the source artefacts, input fingerprints, and upstream packet dependencies from which it was derived where relevant.

## 3.6 Alpha implementation truth

During alpha development, raw inputs may be checked-in specimens, recorded provider responses, local source bundles, workbook-derived reference material, or deliberately incomplete adapters.

Those surfaces must carry structural status and implementation-truth status separately under `docs/11_NATIVE_ARCHITECTURE_BLUEPRINT_CORE.md`. An implementation-truth claim must use the exact governed status values and supporting evidence; a structural `Provisional` or `Reserved` label must not be used as a progress claim. Their existence does not prove live-data readiness, paper-trading readiness, production durability, or end-to-end execution.

The alpha state does not justify fabricated identifiers, untyped cross-boundary payloads, hidden provider coupling, or silent loss of source lineage.

This overlay does not specify production retention periods, recovery objectives, deployment topology, throughput targets, or storage infrastructure. Those requirements remain Unknown until the project reaches the stage at which they can be decided from actual operating needs.

## External-source lineage for this overlay

- Google API Improvement Proposal AIP-122, “Resource names”, reviewed 2026-07-17: supports canonical identifiers with an explicit owning scope and identifiers that persist independently of API-version changes.
- IBM documentation, “Preparing data for data lineage” and “Data lineage”, reviewed 2026-07-17: supports stable source definitions and traceability of where data originated, how it changed, and where it moved.
- Microsoft Azure Architecture Center, “Anti-Corruption Layer pattern”, reviewed 2026-07-17: supports explicit adapters that translate external semantics without allowing external-system shapes to corrupt the internal domain model.
- Microsoft Azure Architecture Center, “Event-Driven Architecture Style” and “Event Sourcing pattern”, reviewed 2026-07-17: supports early schema-version strategy, immutable historical evidence, and explicit identifiers for ordered/replayable records.

The project adopts only the identifier-scope, adapter-isolation, versioning, and lineage principles. It does not adopt event sourcing, distributed messaging, microservices, or production infrastructure as a blanket architecture requirement.
