## Semantic gate acceptance law

A normative semantic unit may be accepted only after the worker has personally performed all of the following in context:

1. read the selected core document in full;
2. read its working companion in full where present;
3. read every materially related normative proposition needed to understand the unit as part of the whole architecture;
4. identify the exact system meaning, owner, status, extension boundary, and relationship to other propositions;
5. classify material propositions truthfully, including ambiguity, contradiction, overclaim, underspecification, reservation, provisional-alpha status, or supersession where applicable;
6. consult authoritative external material only where the project meaning needs external grounding, and record the project-specific adaptation rather than importing vendor text as authority;
7. make the smallest lawful amendment or addendum that resolves the identified issue without rewriting unrelated accepted doctrine;
8. reread the changed normative unit in full;
9. perform a fresh cross-document semantic comparison against all related propositions;
10. run mechanical validation and record the evidence, acceptance result, known truths, ruled-out interpretations, and next semantic unit.

Search, grep, scripts, inventories, generated tables, hashes, line counts, ASTs, embeddings, summaries, test results, or model-generated comparison artefacts may assist navigation and deterministic checking. They must not decide or certify semantic equivalence, contradiction, completeness, architectural adequacy, modularity, future-proofing, or acceptance.

A green test, clean diff, commit, receipt, manifest, or completed checklist cannot close a semantic gate by itself. Conversely, a semantic decision without inspectable source reading, changed text, and mechanical validation is also incomplete.

## Lawful scope-reopening law

The core instruction to stop and reopen a bounded pack means: stop mutation of the current unit, amend the current route and task-local ledger before touching the newly required surface, then resume only after the new classification is explicit. It does not mean that the user must be interrupted for every in-programme route correction.

Within this already authorised programme, the worker may reopen the current bounded pack without further user approval only when all of the following are true:

- the new surface is necessary to resolve the currently selected semantic proposition or its directly governed block;
- the surface remains inside the objective, authority class, and non-destructive boundaries of the ExecPlan;
- the reason, read requirement, mutation classification, and validation obligation are recorded before the surface is touched;
- no new product meaning, production requirement, external side effect, credential use, destructive action, or branch publication is introduced.

A new architecture choice that cannot be derived from existing user intent and accepted doctrine, a destructive action, unavailable required source, external side effect, unsafe tool state, or scope outside the programme remains a user stop gate.

## Git, evidence, and receipt truth

Before and after each bounded mutation, current branch and working-tree state must be inspected. Unrelated changes must not be absorbed, discarded, or represented as programme work. Tests and proof tools must not leave tracked governed artefacts changed; any unexpected mutation must be captured as evidence, restored exactly, and classified before continuation.

Ledgers, manifests, receipts, reports, commits, and proof output record what was read, decided, changed, or executed. They do not create project intent, supersede normative doctrine, or prove target-surface implementation merely by existing. Implementation truth requires evidence from the actual target behaviour at the applicable later gate.

A gate closes only when the normative text, active route, task-local ledger, read manifest, proposition record, validation record, and Git state agree on the same bounded truth.

## Validation execution and evidence-retention law

Required targeted, affected, aggregate, architecture, vocabulary and shadow
checks still execute when routed. Evidence retention must be proportional to the
claim:

- retain one concise summary with exact command or command locator, declared
  environment/interpreter, exit status, counts, failing-node identity and delta,
  material warnings or unavailable checks, and pre/post Git state;
- use the latest accepted comparable checkpoint as the baseline node set rather
  than rerunning unchanged baseline proof solely to reproduce output;
- do not commit full successful stdout/stderr, duplicate baseline/current
  transcripts, JUnit XML, whole-tree hash lists or repeated unchanged command
  output by default;
- retain raw output only when it contains a novel regression, non-deterministic
  result, material environment failure, or evidence expressly required by a
  high-consequence independent review;
- rerun the baseline when its admitted set, environment, command route or
  comparability is stale, changed or Unknown.

This changes retained evidence volume only. It does not authorise skipped proof,
weakened assertions, hidden failures, narrowed collection or a claim that an
unexecuted command passed.
