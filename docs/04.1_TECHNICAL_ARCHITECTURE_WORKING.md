## 4.1 Target technical shape versus current alpha composition

The statement in the core that the serial runtime path “is implemented as an ordered six-stage structure” defines the required technical organisation of that path. It does not establish that every stage is behaviourally complete, lawfully connected, or exercised in an end-to-end governed run.

Current technical implementation truth must be stated per architecture surface through the exact implementation-truth statuses in `docs/11_NATIVE_ARCHITECTURE_BLUEPRINT_CORE.md` and supported by code and proof evidence.

An independently executable stage, service, shell, or packet builder is not proof that its upstream inputs, downstream consumers, persistence, replay, or neighbouring stages are composed lawfully.

A complete-run entry point must not bridge a missing technical lane with fabricated packets, placeholder decisions, default identifiers, or silent fallbacks.

## 4.2 External adapters and typed native ingress carriers

External provider payloads, API responses, checked-in reference artefacts, recorded responses, and operator source bundles cross into native architecture only through an explicit adapter or source reader and a typed native ingress carrier.

The external adapter or source reader owns:

1. provider-protocol handling;
2. preservation of the original source material or its immutable captured representation;
3. provider-field mapping;
4. source-shape validation;
5. declaration of any missing, unavailable, degraded, or unsupported source facts;
6. construction of the applicable typed native ingress carrier.

It must not own candidate formation, risk permission, playbook selection, capital deployment, broker instruction, position state, exit/close policy, or review conclusions.

Each typed native ingress carrier must expose the admission and identifier facts required by `docs/03.1_DOMAIN_MODEL_WORKING.md` through explicit typed fields and an input-family-specific payload contract.

Exact common field names beyond the admitted source temporal fields remain `Reserved` until the top-down carrier/schema boundary is semantically inspected in Gate B. That reservation does not permit omission, generic dictionaries, payload-shape inference, or fabricated identity.

Provider-specific semantics must terminate at the adapter boundary. Downstream preparation and cognition depend on native contracts, not on concrete provider classes, provider field names, transport libraries, or provider-specific dictionaries.

New providers and input families are selected through controlled registration or configuration at the application assembly boundary. Unrelated domain stages must not directly instantiate or branch on every concrete provider implementation.

## 4.3 Repo-wide source temporal standard

This section admits the repo-wide source temporal standard.

This standard sits above DMPV3 packet carriage.
It governs raw captures, local capture files, derived raw surfaces, persistence records, workbook-derived specimens, replay/proof surfaces, and packets where relevant.
It is provider-agnostic.
It must support IBKR-style market data, FRED-style date-level data, and workbook-derived mixed-date reference-ledger specimens without overfitting to one provider.

The governed source temporal fields are:

- `source_time_raw`: the exact source-supplied time token as captured from the source artefact
- `source_time_kind`: the declared kind of source temporal truth carried by the source artefact
- `source_timezone_raw`: the source-supplied timezone or offset label when the source declares one
- `source_time_utc`: the UTC-normalised source observation time only when lawful source truth exists to normalise it
- `source_date`: the source observation date carried or derived without inventing finer precision than the source supplied
- `captured_at_utc`: the UTC time when the repo captured or ingested the source artefact
- `persisted_at_utc`: the UTC time when the repo persisted the record or artefact
- `source_provider`: the upstream provider identity for the observed source artefact
- `source_channel`: the acquisition channel or provider-local lane for the observed source artefact
- `time_granularity`: the source observation granularity admitted by the source truth

`source_time_utc` and `source_date` record source observation truth.
`captured_at_utc` and `persisted_at_utc` record repo process timing.
`captured_at_utc` and `persisted_at_utc` must not be substituted for source observation time.

Where the source provides only date-level truth, `source_date` is authoritative and no finer source timestamp must be invented.
Where the source provides local-clock time with a declared timezone or offset, `source_time_raw`, `source_timezone_raw`, and `source_time_utc` must remain mutually consistent.
Where a workbook-derived specimen blends fields with different source dates, the specimen must preserve field-level provenance rather than fabricate one false same-moment source timestamp.

## 4.4 DMPV3 carriage boundary and identifier separation

DMPV3 is the canonical outer envelope for deliberate live inter-module packet carriage. It is not the universal raw-source storage shape and it does not replace input-family-specific typed carriers or payload contracts.

The canonical packet builder owns creation of packet-carriage identity and emission metadata. The producing domain module owns the payload meaning and must supply the source, domain, decision, state, and dependency identities required by its contract.

A packet builder must not generate substitute source, candidate, decision, position, execution, receipt, or state identifiers merely because a required value is missing.

DMPV3 `id`, `source`, `traceid`, `runid`, `scenarioid`, `producer`, and `lineage` are carriage and execution-context facts with the bounded meanings governed by `docs/09_DMPV3_PROTOCOL_CORE.md` and its admitted overlays. Payload and lineage must preserve upstream authoritative identities separately where the contract requires them.

A common DMPV3 envelope standardises carriage only. It must not cause module-specific payload contracts to collapse into an untyped common payload.

## 4.5 Dependency direction and implementation substitution

Domain and application behaviour must depend on explicit contracts or interfaces for external sources, persistence, clocks, identifiers, configuration, and other replaceable infrastructure.

Concrete adapters, repositories, stores, clocks, and infrastructure clients are selected and wired at an explicit application assembly boundary. They must not be instantiated inside unrelated domain decisions or hidden behind module-global mutable state.

One concrete implementation may be replaced by another without changing the meaning or internal rules of unrelated domain stages, provided both satisfy the same admitted contract.

This dependency direction applies inside a modular monolith. It does not require microservices, distributed deployment, dynamic plugin loading, or a particular dependency-injection framework.

## 4.6 Alpha persistence implementations

A repository or store contract defines a state boundary. Its name or interface does not prove that a concrete implementation is durable.

An in-memory implementation is lawful during alpha development when:

1. it is labelled as volatile and non-durable;
2. it is selected behind the same bounded repository or store contract expected of a later implementation;
3. its owning state domain, authoritative writer, readers, duplicate/append rules, and fallback behaviour are explicit;
4. tests and documentation do not describe process-memory survival as restart persistence or replay completeness.

A concrete implementation may be described as durable only when the stored truth survives process termination and can be read by a new process through the declared state boundary, with direct proof for the claimed behaviour.

The presence of a database client, ORM, migration tool, or driver in project dependencies indicates an available implementation technology only. It does not by itself lock the persistence architecture or prove that any runtime state uses that technology.

Production retention, recovery, availability, scaling, backup, and deployment requirements remain outside this alpha supplement.

## 4.7 Re-execution and preserved-envelope proof

Replay-related proof must distinguish two different questions.

First, governed re-execution asks whether the same authoritative captured inputs, contract versions, material configuration and policy versions, ordered dependencies, and algorithm/module versions produce the same domain result and deterministic semantic fingerprint.

Second, preserved-envelope evidence asks whether the original emitted packet, including its original packet identity and emission metadata, can be retrieved and inspected as originally recorded.

A newly emitted replay-result packet is a new carriage occurrence. Its packet identity, emission time, run context, or replay trace may differ from the original only under an explicit replay contract. It must identify the original evidence and must not be compared byte-for-byte as though process metadata were part of the deterministic domain result.

Where exact original-envelope reproduction is claimed, the original envelope must be preserved and read back. It must not be regenerated from a current wall clock and presented as the original.

Deterministic semantic fingerprints must exclude fields whose governed meaning is current process emission metadata, while including every material source, contract, configuration, policy, dependency, and algorithm version that can change the domain result.

This alpha replay law does not require event sourcing or a production event store. It requires honest proof boundaries and enough preserved evidence to explain what can and cannot be reconstructed.

## 4.8 Prepared context support-spine supplement

`ROADMAP_SUPPORT_SPINE_5H_BRANCH_001` admits a bounded support-spine handoff from raw source-temporal material into prepared runtime context, canonical packet carriage, and deterministic review explanation.

The prepared context handoff is a support surface. It may preserve source temporal standard truth, preparation lineage, derived-field names, missing optional enrichments, failed enrichments, and deterministic packet fingerprints. It must not decide trades, position size, capital deployment, risk permission, or broker instructions.

The lawful packetised support-spine output is a `prepared_context_packet` emitted by the prepared-ingress authority. Review/explanation may consume packet lineage and emit review-only explanation material, but that explanation does not become runtime decision authority.
