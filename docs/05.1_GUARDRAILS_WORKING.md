# 05.1_GUARDRAILS_WORKING

All repo paths in the numbered control stack are repo-root-relative.

## Status

This working overlay contains admitted alpha-stage guardrails supplementing `docs/05_GUARDRAILS_CORE.md`.

The core prohibition against convenience replacing authority remains binding. This overlay adds precise absence, identifier, modularity, persistence, replay, proof, and alpha-truthfulness guardrails without creating trading policy or production requirements.

## 5.1 Guardrail scope versus trading policy

The guardrails in `docs/05` protect architecture meaning, ownership, lineage, validation, proof integrity, and honest status.

They do not define a market view, strategy, playbook, position size, risk threshold, coefficient value, capital-deployment percentage, exit trigger, or broker instruction.

A numeric or behavioural trading constraint must be owned by its admitted domain policy or configuration authority. It must not be smuggled into a structural guardrail merely because the constraint sounds conservative.

Likewise, a domain policy must not be used to waive structural ownership, lineage, contract, or proof requirements.

## 5.2 Required and optional absence guardrail

Every typed contract must distinguish required facts from optional facts and state the lawful consequence of absence.

Where a required identity, authority, input, policy, dependency, or validation fact is absent, the affected admission, decision, state transition, or complete-run path must fail closed or stand down.

For this repository, fail closed means that the system does not issue the binding output or transition whose prerequisites are missing. It may return an explicit rejection, non-admission, blocked result, diagnostic, or review record. It does not require an unhandled process crash.

Where an optional enrichment is absent, the system may continue only when the governing contract expressly permits it. The absence, limitation, and effect must remain explicit; the system must not fabricate a value, silently promote a fallback, or relabel the result as fully enriched.

A warning cannot downgrade a missing mandatory fact into an optional fact. A default cannot create authority that the owning contract requires from elsewhere.

## 5.3 Identifier and lineage guardrails

The following moves are prohibited:

- manufacturing a source, candidate, decision, position, execution, receipt, or state identifier downstream of its lawful owner;
- replacing a missing authoritative identifier with a packet ID, trace ID, run ID, scenario ID, correlation value, timestamp, filename, hash, array position, or random value;
- changing the meaning or scope of an identifier while preserving its field name;
- claiming global uniqueness when the owner guarantees uniqueness only inside a narrower source or namespace;
- dropping source artefact, input fingerprint, dependency, policy, or decision lineage required to explain a material result;
- treating packet-carriage lineage as proof that the underlying domain lineage exists when the required domain identifiers are absent.

A repository-owned capture identity is lawful when it truthfully names captured evidence. It must not masquerade as a source-issued identity.

## 5.4 Modularity and extension guardrails

The following moves are prohibited:

- hard-coding a fixed number of providers, input families, playbooks, policies, adapters, persistence implementations, or review views into unrelated orchestration;
- placing provider-specific fields or protocols inside downstream domain logic;
- replacing strongly typed payload contracts with generic dictionaries or payload-shape guessing;
- creating a central switch statement that must be edited for every implementation when a bounded registry, configuration, or contract-owned selection seam is required;
- using module-global mutable state to hold material policy, risk, capital, position, execution, or persistence authority;
- requiring unrelated stages to change when one contract-conforming implementation is added, removed, or replaced;
- introducing abstraction, interfaces, services, or deployables where no present volatility, ownership, proof, or substitution boundary justifies them.

Future-proofing requires explicit seams at known change boundaries. It does not justify framework construction for hypothetical variation.

## 5.5 State, persistence, and replay guardrails

The following moves are prohibited:

- calling process-memory state durable, persisted, restart-safe, or replay-complete;
- inferring active persistence from a repository/store name, database driver, ORM, migration file, schema, or unused dependency;
- allowing more than one authoritative writer for the same state domain without an explicit reconciliation rule;
- allowing a bootstrap, fixture, example registry, recorded response, or fallback implementation to become normal runtime authority silently;
- using current wall-clock emission metadata as part of a deterministic domain-result fingerprint;
- claiming exact original-packet replay when a new packet was emitted with regenerated identity or time;
- claiming deterministic reconstruction while omitting a material source, contract, configuration, policy, dependency, or algorithm version.

In-memory alpha implementations may remain lawful when their volatility and bounded contract are explicit. This guardrail does not require premature production storage or operations machinery.

## 5.6 Proof and alpha-truthfulness guardrails

The following moves are prohibited:

- describing an independently tested component as an end-to-end governed system;
- using a green local test to prove an untested ownership, integration, restart, replay, substitution, or complete-run claim;
- allowing a test to mutate a tracked governed artefact and then treating the changed artefact as proof input;
- weakening validation, suppressing a failing proof, editing expected evidence, or creating a fake fixture to make current code appear compliant;
- using current code, tests, receipts, roadmaps, or audit prose to reverse-create normative intent;
- presenting a `thin_seam`, `placeholder`, `reserved`, `future_only`, or `legacy_only` surface as completed native behaviour;
- inventing production retention, recovery, deployment, availability, scaling, paper-trading, or live-readiness claims during alpha.

A proof must state exactly what was exercised and what remains Unknown.

## 5.7 Temporal anti-drift guardrails

- Do not invent timestamp precision that the source did not provide.
- Do not apply fake UTC normalisation where lawful source truth is absent.
- Do not collapse mixed-date reference sources into one false observation timestamp.
- Do not let module-local temporal grammars diverge from the repo-wide source temporal standard admitted in `docs/04.1_TECHNICAL_ARCHITECTURE_WORKING.md`.
- Do not substitute `captured_at_utc`, `persisted_at_utc`, or packet emission time for source observation time.

## External-source lineage for this overlay

- NIST least-privilege and least-functionality principles, reviewed 2026-07-17: support giving each component only the authority and functions required for its bounded job.
- NIST fail-safe and fail-secure definitions, reviewed 2026-07-17: support preserving a safe state when required authority or validation fails, adapted here as withholding the binding output rather than requiring a process crash.
- IBM validation guidance, reviewed 2026-07-17: distinguishes blocking missing required inputs from non-blocking warnings and supports explicit validation outcomes.
- Google Cloud Architecture Framework, “Promote modular design”, reviewed 2026-07-17: supports clear interfaces and independent updates while warning against modularity overhead that does not fit the system.
- Microsoft Learn, “Common web application architectures”, reviewed 2026-07-17: supports dependency inversion and infrastructure substitution without importing infrastructure details into domain logic.

These principles are adapted to architecture and proof integrity in an alpha trading-cognition codebase. They do not create security certification, production controls, or trading policy.
