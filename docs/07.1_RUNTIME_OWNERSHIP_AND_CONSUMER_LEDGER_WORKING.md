# Runtime Ownership and Consumer Ledger — Working Overlay

This working overlay records bounded additions to `docs/07_RUNTIME_OWNERSHIP_AND_CONSUMER_LEDGER_CORE.md`. It does not replace the core ownership law.

## 7.1 Alpha ownership and state-authority model

The core one-owner/one-meaning rule governs semantic ownership. This overlay adds the alpha-stage distinctions needed to prevent an implementation file, repository interface, packet, receipt, or review surface from silently becoming authority for a different question.

For every material output or state domain, the architecture must distinguish these roles where they apply:

- **semantic owner** — defines the bounded meaning, invariants, and lawful decisions of the output or state;
- **authorised emitter or state writer** — is the only bounded component permitted to originate the material output or mutate the owned state;
- **coordinator** — may sequence calls and carry results but does not acquire the semantic authority of the components it coordinates;
- **persistence owner** — defines the repository or store boundary, duplicate/update law, and readback contract for retained state;
- **reader or consumer** — reads through the declared carrier, query, repository, or store contract and must not infer authority from internal representation;
- **review or explanation owner** — may describe preserved outputs and limitations but must not rewrite the decisions or state it reviews.

A Python module, class, service, endpoint, test, or receipt path is implementation evidence or a target allocation. Its location does not by itself create normative ownership, prove that the target owner is correctly implemented, or prove that the state is durable.

## 7.2 Required ownership record

Before a material boundary can be called aligned, its ownership record must state, at minimum:

1. architecture surface and bounded question answered;
2. semantic owner;
3. authorised emitter or state writer;
4. lawful readers and downstream consumers;
5. input and output carrier or contract;
6. material identifier owners and propagation obligations;
7. structural status and implementation-truth status;
8. current state-retention class and concrete implementation truth;
9. duplicate, update, append, or replacement rule where state exists;
10. minimum facts required for governed re-execution and preserved-envelope evidence;
11. required-absence and fail-closed behaviour;
12. forbidden authority mixing;
13. replacement or extension boundary;
14. direct evidence and unresolved `Unknowns`.

This record is semantic architecture law. Gate B must populate it boundary by boundary through full reading of the applicable contracts, tests, code, configuration, and state surfaces. A generated inventory or matching field name cannot establish any of these answers.

## 7.3 Alpha state-retention truth

Current state must be described by what the concrete implementation actually retains:

- a derived output that is not retained beyond the call is transient;
- a list, dictionary, singleton, module global, or object-held repository that disappears on process termination is process-memory state and is non-durable;
- checked-in configuration or reference material is repository-versioned input, not runtime state merely because runtime code reads it;
- a receipt or artefact written to a file is file-retained only to the extent proved by the actual write and readback path;
- state is database-backed only where the active path writes and reads that state through the declared database boundary;
- a placeholder or reserved surface has no current material state authority beyond the explicitly admitted shell or specimen behaviour.

A repository contract may define the future durable boundary while its current alpha implementation remains process-memory and non-durable. JSON serialisability, copy-on-read, duplicate rejection, append-only behaviour, an ORM dependency, a migration tool, or a database driver does not independently prove restart survival.

This alpha classification does not choose production storage technology, retention periods, backup policy, recovery objectives, deployment topology, capacity, or availability requirements. Those remain outside current authority.

## 7.4 Minimum replay envelope

For every material deterministic decision or state transition, the owning boundary must identify the minimum logical facts needed to explain and, where claimed, re-execute that result. The applicable typed contracts must preserve or reference:

- authoritative source or captured-input identities and fingerprints;
- input contract and schema versions;
- source observation or effective time facts, distinct from process emission time;
- material configuration, policy, coefficient, playbook, and algorithm/module versions that can change the result;
- upstream decision, packet, receipt, and state-snapshot identities actually consumed;
- the bounded output or transition identity;
- deterministic semantic result fingerprint where the domain supports one;
- explicit missing, optional, blocked, or non-applicable facts;
- original packet or receipt identity when preserved-envelope evidence is claimed.

The exact field names and per-boundary mandatory subset remain to be fixed during the Gate B semantic walk. The system must not fabricate missing facts, treat a new packet as the original envelope, or describe a locally deterministic function as end-to-end replay proof.

## 7.5 Writer, reader, and substitution law

Only the authorised writer may originate or mutate the truth owned by a material state domain. A coordinator, API adapter, packet builder, review layer, test, or downstream consumer may carry, request, validate, or describe that truth only through its declared contract.

A reader must not access private repository representation, shared mutable objects, or implementation internals when a lawful read contract exists. A read model may differ from the write model, but it must preserve the owned meaning and identify its source state.

A concrete provider, repository, configuration source, audit sink, scheduler, user interface, playbook family, or policy implementation is replaceable only through its owning contract and explicit assembly or registration boundary. Replacement must not require unrelated domain owners to absorb provider-specific fields or implementation branches. This applies inside the modular monolith and does not require microservices, separate databases, dynamic plugin machinery, or distributed messaging.

## 7.6 Implementation-status constraint on retained supplements

The ownership supplements below preserve bounded target meaning and forbidden mixing. Their historical words `active`, `authoritative writer`, or named source paths do not independently establish current implementation maturity, durable persistence, end-to-end composition, or mutation authority.

Current structural and implementation-truth status is governed by `docs/11_NATIVE_ARCHITECTURE_BLUEPRINT_CORE.md` and `docs/11.1_NATIVE_ARCHITECTURE_BLUEPRINT_WORKING.md`. The programme implementation-truth ledger records evidence only and cannot change status.

- a `thin_seam` remains incomplete and may participate only within its admitted bounded alpha contract;
- a `placeholder` remains a shell and cannot be treated as complete domain authority;
- a `reserved` or `future_only` surface must not participate as current governed runtime authority.

Substantive but incomplete native alpha behaviour exists for each. This admits bounded contracts and local alpha participation only; it does not prove algorithmic correctness, replaceability, trustworthy lineage, durable state, complete composition or operational authority.

## 7.7 M07 K12 coefficient/modifier bundle, decision and receipt law

This section closes the positive architecture obligation identified as contract `K12` and cohort decision `C-012` for module `M07`. It governs only coefficient and modifier authority. The word `policy` in `PolicyBundle` is therefore local to M07's bounded coefficient/modifier policies and must not be read as calendar, playbook, capital, execution, lifecycle, replay or global strategy authority.

### 7.7.1 Canonical public contracts and ownership

M07 owns three public contracts:

1. `PolicyBundle` — one immutable, versioned M07 coefficient/modifier authority bundle;
2. `ModifierDecision` — one deterministic, side-effect-free resolution result for a valid bundle and identified input-state facts;
3. `ModifierApplicationReceipt` — immutable evidence that one non-rejected decision was resolved for one owner stage and application context.

M07 owns bundle validation, coefficient/modifier identity, deterministic ordering, conflict resolution, hard-bound enforcement, resolution status and receipt meaning. It does not own the upstream facts used to determine whether a modifier is applicable. It must consume those facts through identified, versioned or fingerprinted owner contracts. It must not infer state from ungoverned strings, current wall-clock time, mutable globals, caller order or hidden runtime observation.

A `ModifierApplicationReceipt` records M07 resolution/application evidence only. It is not an M12 replay result, an M13 transaction receipt, a capital decision, a strategy-selection receipt or proof that a downstream owner mutated state.

### 7.7.2 PolicyBundle identity, version and member law

A valid `PolicyBundle` must declare, at minimum:

- `bundle_id`, `bundle_version`, `schema_version`, `authority_id` and `authority_version`;
- one explicit effective-version interval or equivalent promoted-version selector;
- an immutable coefficient-member collection and an immutable modifier-member collection;
- the bundle's deterministic resolution-law version;
- promotion/workbook lineage sufficient to identify the admitted authority source.

Bundle identity and version are inseparable. An unknown, missing, superseded-without-compatible-selection or schema-incompatible version fails closed. A caller may request a bundle by identity/version but may not construct an authoritative bundle by supplying an arbitrary mapping.

Each coefficient member must declare a unique coefficient identity and version, exact owner stage, value type and units, baseline value, hard lower and upper bounds, surface class, admitted transform family, runtime-mutability class and promotion/workbook lineage. Baseline and bounds must be finite and type-compatible; the baseline must lie inside the hard bounds. Any declared threshold ordering or asymmetric law is part of the member authority and must be validated before resolution.

Each modifier member must declare a unique modifier identity and version, exact target coefficient identities, the same lawful owner stage as those targets, explicit applicability fact references, precedence rank, transform operator and operand, compatibility/combination law, conflict or veto relations, and any kill-switch or restrictive-only status. A modifier may target only admitted mutable coefficient members. It may not create a new coefficient, widen a target's hard bounds, replace the owner stage, select a playbook, allocate capital or mutate an external state owner.

A bundle with no coefficient members is invalid. A valid bundle may contain no modifier members; that is an explicit no-modifier bundle, not a missing bundle.

### 7.7.3 Applicability, lawful absence and fail-closed outcomes

The following states are distinct:

- **missing or invalid bundle** — resolution is rejected; no binding effective values and no `ModifierApplicationReceipt` may be emitted;
- **valid bundle with no modifier members** — resolution is a valid no-op preserving every baseline;
- **valid bundle with modifier members but none applicable** — resolution is a valid no-applicable-modifiers outcome preserving every baseline;
- **valid bundle with applicable modifiers** — deterministic precedence, conflict and bounds law applies.

Missing applicability facts are not equivalent to a false condition unless the owning fact contract explicitly defines that equivalence. An unavailable, stale, incompatible or unidentifiable material fact must reject or withhold the affected resolution rather than activate a modifier or silently use a default.

A rejected `ModifierDecision` may identify the requested bundle reference, owner stage and exact failed authority facts, but it must not fabricate a valid bundle identity, effective values or successful application. Only `applied`, `no_modifier_members` and `no_applicable_modifiers` decisions may produce a `ModifierApplicationReceipt`.

### 7.7.4 Deterministic precedence and conflict law

For a valid bundle and complete admitted input facts, M07 must:

1. validate unique member identities, versions, owner stages, targets, types, bounds and transform families;
2. evaluate applicability only from the declared input-fact references;
3. order applicable modifiers by authority-owned precedence, not by caller or container order;
4. apply explicit compatibility/combination law for modifiers sharing a target;
5. make a hard kill switch, hard block or explicit veto dominate weaker scaling or permissive effects;
6. preserve the most restrictive categorical block where several compatible restrictions apply;
7. reject equal-precedence or otherwise unresolved incompatible effects rather than choose arbitrarily;
8. perform admitted bounded algebra in the resolved order;
9. clamp the numeric candidate to the coefficient's hard bounds after bounded algebra and record whether and where clamping occurred.

A stable identity/version tie-break may be used only where the bundle expressly declares the effects compatible and commutative or declares that tie-break as part of the resolution law. Sorting by identity must never conceal a semantic conflict. Boolean, categorical and enumerated surfaces require explicit operator law and must not be coerced through numeric algebra.

No resolution may increase authority beyond the bundle. In particular, M07 cannot use a modifier to open fresh capital, bypass an upstream hard block, widen a coefficient hard bound or convert an unavailable owner fact into permission.

### 7.7.5 ModifierDecision minimum facts

A non-rejected `ModifierDecision` must preserve or reference, at minimum:

- decision identity and deterministic semantic fingerprint;
- bundle, authority, schema and resolution-law identities/versions;
- owner stage and identified input-state/context identity, version, effective time and fingerprint;
- decision status;
- ordered evaluated, applied and skipped modifier identities/versions with exact reasons;
- per-coefficient baseline, pre-clamp candidate, hard bounds, effective value and bound disposition;
- any applicable veto, kill-switch, restriction or conflict disposition;
- closed authority classes showing that capital, playbook, execution, lifecycle and replay authority were not acquired.

The semantic fingerprint must include every material fact that can change the decision and must exclude occurrence-only metadata such as receipt emission time or a random receipt identifier. The same exact bundle/version, resolution-law version and admitted input facts must produce the same semantic decision and fingerprint.

### 7.7.6 ModifierApplicationReceipt minimum facts and side-effect boundary

A `ModifierApplicationReceipt` must preserve or reference, at minimum:

- receipt identity, application identity and source `ModifierDecision` identity/fingerprint;
- bundle, authority, schema and resolution-law identities/versions;
- owner stage and input-state/context identity, version, effective time and fingerprint;
- decision status and the ordered modifier/application facts that produced it;
- per-coefficient baseline, candidate, bounds, effective value and clamp disposition;
- explicit no-op class when no modifier member exists or none is applicable;
- closed authority classes and any limitations;
- receipt emission time, separately labelled as occurrence metadata.

M07 resolution is side-effect-free. A lawful downstream owner may consume a non-rejected decision and mutate only its own state under its own contract. The receipt may attest that the decision was presented to or resolved for that owner-stage context, but it must not claim that an external mutation occurred unless an owner-specific atomic receipt separately proves it.

M12 may later replay or compare M07 evidence using the exact bundle/version, resolution-law version and input facts. That downstream use does not transfer replay authority to M07 and does not permit current code, current configuration or wall-clock state to stand in for the original material set.


## 7.8 M08 K13 playbook definition, catalogue and eligibility-decision law

This section closes the positive architecture obligation identified as contract `K13` and requirements `C-033` and `C-034` for module `M08`. It governs replaceable playbook definitions, the immutable versioned catalogue that contains them, and deterministic eligibility metadata. It does not grant M08 candidate-expression, capital, broker, order, position, exit/close, coefficient, source-ingress or global strategy authority.

### 7.8.1 Canonical public contracts and ownership

M08 owns three public contracts:

1. `PlaybookDefinition` — one immutable, versioned definition of a catalogue-owned candidate family and its bounded eligibility and handoff metadata;
2. `PlaybookCatalogue` — one immutable, versioned M08 authority snapshot containing the admitted definitions and the exact eligibility-resolution law;
3. `EligibilityDecision` — one deterministic, side-effect-free result binding an identified catalogue snapshot to identified posture and eligibility-context facts.

M08 owns definition and catalogue validation, candidate-family identity within the catalogue, eligibility-constraint meaning, deterministic candidate ordering, eligibility-lead metadata, decision status/reasons and decision fingerprinting. M05 owns serial-stage orchestration, candidate expression and the final serial candidate. An M08 eligibility lead is therefore only the first eligible catalogue candidate under K13 ordering; it is not a trade recommendation, capital decision, execution instruction or final expressed candidate.

M08 consumes upstream facts only through identified owner-issued contracts. It must not infer posture, signals, calendar state, coefficients or market context from ungoverned strings, current wall-clock time, mutable globals, caller/container order or hidden runtime observation. Consuming those owner-issued facts through M05 orchestration does not create a direct runtime dependency from M08 to their producing modules.

### 7.8.2 PlaybookCatalogue and PlaybookDefinition identity/version law

A valid `PlaybookCatalogue` must declare, at minimum:

- `catalogue_id`, `catalogue_version`, `schema_version`, `authority_id` and `authority_version`;
- one explicit effective-version interval or equivalent promoted-version selector;
- the catalogue's deterministic `eligibility_law_version`;
- an immutable collection of `PlaybookDefinition` members;
- promotion/workbook lineage sufficient to identify the admitted authority source;
- a deterministic catalogue fingerprint over all material authority content.

Catalogue identity and version are inseparable. A replacement, removal, enable/disable change, constraint change, priority change or lifecycle-metadata change creates a new catalogue version; a promoted snapshot is never mutated in place. An unknown, missing, superseded-without-compatible-selection, schema-incompatible or fingerprint-mismatched catalogue is rejected. A caller may request an admitted catalogue identity/version but may not create authority by supplying an arbitrary mapping or by relying on the checked-in example registry.

A valid `PlaybookDefinition` must declare, at minimum:

- unique `playbook_id` and `playbook_version`;
- unique `candidate_family_id` and `candidate_family_version` owned by that definition within the catalogue;
- any setup-variant identities and versions that the definition may emit;
- an explicit integer `selection_priority`, where the lower value is the stronger catalogue priority;
- typed eligibility constraints with exact fact references, operators, comparison values and requiredness/default law;
- explicit enabled/disabled state;
- bounded declarative lifecycle-intent or handoff metadata and its schema/version;
- promotion/workbook lineage.

Candidate-family and setup-variant identities are catalogue authority, not caller labels. Their scope, uniqueness and stability are the exact catalogue/version in which they are declared. Reusing one identity for a different meaning is prohibited; changing meaning requires a new member version and, because the snapshot changed, a new catalogue version.

A catalogue with no definitions is invalid. A valid catalogue may contain only disabled definitions; that is a lawful no-candidate catalogue state and is distinct from missing catalogue authority.

### 7.8.3 Mandatory eligibility inputs and constraint evaluation

One M08 resolution requires:

- one exact `PlaybookCatalogue` identity/version/fingerprint;
- one posture-permission fact carrying owner identity, contract/version, status, effective or as-of time and semantic fingerprint;
- one eligibility-context fact set carrying context identity, contract/version, effective or as-of time and semantic fingerprint;
- every owner-issued signal, calendar, event or other fact required by an enabled definition, each with its owner identity/version and material value lineage.

The posture-permission input is mandatory even though posture precedes eligibility in the serial spine. `blocked` posture produces the lawful stand-down in section 7.8.4; missing, stale, incompatible or unidentifiable posture authority rejects the decision.

M08 evaluates only constraints declared by enabled definitions. A required fact that is missing, stale, incompatible or unidentifiable rejects the resolution rather than being treated as false, supplied from a default, or skipped. A default is lawful only when the definition explicitly declares the default and the owning fact contract permits that absence semantics. Unknown operators, malformed constraints, duplicate identities, undeclared family/variant references or forbidden-authority fields invalidate the catalogue.

### 7.8.4 Rejection and lawful stand-down states

The following outcomes are distinct:

- **rejected** — catalogue authority, mandatory posture/context authority, required fact authority or contract integrity is missing or invalid; no binding eligible list or eligibility lead may be emitted;
- **stand_down_posture_blocked** — all authority is valid and the owner-issued posture status blocks progression;
- **stand_down_no_candidate_families** — the catalogue is valid but contains no enabled candidate-family definitions;
- **stand_down_no_eligible_candidates** — at least one enabled definition was lawfully evaluated and none satisfied its constraints;
- **eligible** — one or more definitions lawfully satisfied their constraints and an ordered eligible-candidate list is emitted.

A rejected decision may identify the requested catalogue reference and exact failures, but it must not fabricate a valid catalogue fingerprint, candidate family, eligible list or lead. Stand-down decisions must preserve the exact valid catalogue and input lineage that produced the empty outcome. Empty list, missing authority and posture block are never interchangeable.

### 7.8.5 Deterministic filtering, ordering, tie-break and lead law

For a valid catalogue and complete admitted input facts, M08 must:

1. validate catalogue, definition, family and variant identity/version uniqueness and all declared constraint and handoff schemas;
2. skip disabled definitions with the exact `disabled` reason;
3. evaluate enabled definitions against only their declared owner-issued facts;
4. record each evaluated definition as eligible or ineligible with exact constraint dispositions;
5. order eligible candidates by ascending authority-owned `selection_priority`;
6. break equal priorities lexicographically by the stable tuple `(candidate_family_id, candidate_family_version, playbook_id, playbook_version, setup_variant_id, setup_variant_version)`, using an empty setup-variant component only where the definition lawfully emits no variant;
7. expose the first ordered candidate as `eligibility_lead` when and only when status is `eligible`.

Catalogue member order, mapping order, caller order and service/orchestrator order must not affect the result. An equal-priority tie is not a conflict because K13 expressly owns the stable identity/version tie-break above. A caller-provided family order or lead hint has no authority and must be ignored or rejected rather than used as the selection rule.

M08 ordering is selection metadata for M05. M05 may form or decline to form a final serial candidate under its own contract, but it may not silently reorder K13 eligibility metadata while claiming the result is the original M08 decision.

### 7.8.6 EligibilityDecision minimum facts and fingerprint law

An `EligibilityDecision` must preserve or reference, at minimum:

- decision identity, decision schema/version and deterministic semantic fingerprint;
- catalogue, authority, schema and eligibility-law identities/versions plus catalogue fingerprint and promotion/workbook lineage;
- posture-permission identity/version/status/effective time/fingerprint;
- eligibility-context identity/version/effective time/fingerprint and all material required-fact lineage;
- decision status and exact top-level reasons;
- ordered skipped, evaluated-ineligible and eligible definition/family/variant identities/versions with exact reasons;
- the complete ordered eligible-candidate list and `eligibility_lead`, or an explicit lawful absence for non-eligible states;
- bounded lifecycle-intent/handoff metadata carried from each eligible definition without reinterpretation;
- closed authority classes showing that capital, broker execution, order, position/inventory, exit/close, coefficient, source-ingress, replay and transaction authority were not acquired.

The semantic fingerprint must include every material catalogue and input fact that can change filtering, ordering or outcome. It must exclude occurrence-only metadata such as emission time or a random decision occurrence identifier. The same exact catalogue/version/fingerprint, eligibility-law version and admitted input facts must produce the same semantic decision and fingerprint.

### 7.8.7 Lifecycle carriage, state, replay and side-effect boundary

A `PlaybookDefinition` may carry only bounded declarative lifecycle-intent metadata required by the later serial expression and downstream lifecycle contracts, such as an identified horizon class, management-tag set or handoff-schema reference. M08 may validate and carry that metadata unchanged. It must not calculate position size, allocate capital, choose a broker/order instruction, mutate a position, trigger an exit/close action or decide portfolio lifecycle state.

M08 resolution is side-effect-free. Its state class is immutable repository/configuration authority plus emitted decision metadata only. Catalogue promotion or replacement is an external governed configuration action that selects a new immutable version; eligibility resolution must not edit the catalogue or learn a new rule from runtime observations.

M12 may later replay or compare an `EligibilityDecision` using the exact catalogue snapshot, eligibility-law version and input facts. That downstream use does not transfer replay authority to M08 and does not permit current configuration, current code or wall-clock state to stand in for the original material set.

## 7.9 M02 K04 Financial Calendar Snapshot, Calendar Fact Candidate and Calendar Projection law

This section closes the positive architecture obligation identified as contract `K04` and requirements `C-005` and `C-018` for module `M02`. It governs only financial-calendar facts, their lawful coalescence or supersession, and deterministic runtime projection. It does not admit session-phase behaviour, candidate formation, risk permission, capital, order, position, lifecycle or review authority.

### 7.9.1 Canonical public contracts and ownership

M02 owns three public contracts:

1. `CalendarFactCandidate` — one immutable, owner-issued calendar fact candidate from exactly one governed calendar layer;
2. `FinancialCalendarSnapshot` — one immutable, versioned K04 authority snapshot containing the exact four semantic layers and their completeness/conflict state for a stated scope;
3. `CalendarProjection` — one deterministic, side-effect-free projection result selecting, coalescing or withholding calendar facts for a stated effective/as-of window.

M02 owns calendar fact identity, calendar-layer classification, calendar-specific equality/coalescence, explicit supersession validation, unresolved-conflict preservation, snapshot construction and runtime projection. M01 owns admitted source/capture identity and source-time truth. M13 may provide transaction mechanics when M02 mutates calendar state, but it does not acquire calendar meaning. Downstream modules are read-only consumers and determine their own response to degraded or withheld calendar context.

`FinancialCalendarAuthorityBundle`, `ImportedReferenceBundle`, `RuntimeCalendarSnapshot`, `PrecursorRuntimePacket` and `CalendarAuthorityProjectionTrace` are current or transitional implementation surfaces. They may remain only where their meaning is narrowed toward K04 and they do not compete with the canonical public contracts above.

### 7.9.2 CalendarFactCandidate identity and layer law

Every `CalendarFactCandidate` must carry, at minimum:

- one non-empty candidate identity unique inside its declared owner/namespace;
- exactly one `FinancialCalendarLayer` value from the four-layer model in section 03.2.N02;
- one fact family and one semantic key/field;
- the typed value or explicit unavailable/cancelled state;
- effective time or effective interval at source precision;
- source artefact/capture identity, source version and contract/schema version;
- owner/writer identity and validation state;
- observation/capture facts where supplied by the source contract;
- explicit supersession target, reason/status and effective interval when supersession is claimed.

A derived-runtime candidate may describe projection evidence but can never supersede or rewrite a source/reference or operational fact. A candidate ID, source artefact ID, bundle ID, event ID, session ID, context ID and packet ID remain distinct roles and must not be fabricated from one another.

### 7.9.3 FinancialCalendarSnapshot law

A `FinancialCalendarSnapshot` must bind exactly these four named layer collections:

- `market_session_reference`;
- `financial_event_reference`;
- `operational_calendar_state`;
- `derived_runtime_calendar_context`.

It must also preserve snapshot identity, snapshot/schema version, selected reference bundle identities and versions, scope, effective/as-of window, candidate identities, completeness and conflict state, applied supersession decisions, projection-policy version where a derived layer is present, and a deterministic semantic fingerprint under a declared canonicalisation version.

The four layer names are semantic identities, not arbitrary labels. A storage table, provider feed, compatibility packet, source file or in-memory repository does not create a fifth layer. An empty layer collection is lawful only when its absence/completeness state is explicit and the requested projection contract permits it.

### 7.9.4 Coalescence, supersession and conflict law

Calendar resolution is semantic-key and effective-window specific.

1. Candidates may coalesce only when their fact family, semantic key, effective applicability, type/unit and value are equal under an explicit calendar-field comparison rule.
2. Coalescence retains every contributing candidate identity, source identity/version and layer; it must not represent one candidate as silently overwriting another.
3. Unequal candidates require one explicit, versioned resolution rule. A selected reference version may replace an earlier reference version only through bundle/version authority. An operational candidate may supersede one named reference or earlier operational candidate only when all section 03.2.N02.4 conditions are satisfied.
4. Caller order, insertion order, latest capture time, non-empty value, materiality, source-list order or a derived-runtime value must not decide precedence.
5. Incompatible same-key candidates without lawful supersession are an unresolved conflict. If the field is mandatory, no selected value or authoritative projection is emitted. If partial projection is expressly permitted, the field remains unavailable and the conflict evidence is preserved.

A supporting `CalendarFieldResolutionPolicy` or equivalent may encode the comparison and mandatory/optional rule for a semantic field. It is M02 configuration authority and cannot widen the four-layer model or grant a caller discretion to choose a winner.

### 7.9.5 CalendarProjection minimum facts and temporal law

Every `CalendarProjection` must identify:

- projection identity and projection-policy version;
- source `FinancialCalendarSnapshot` identity/version/fingerprint;
- requested scope and effective/as-of window;
- selected semantic fields and values;
- complete contributing candidate and source lineage for each selected value;
- applied supersession decisions;
- unresolved conflicts, missing mandatory authority and optional/degraded facts;
- exact status: `projected`, `degraded`, `withheld` or `rejected`;
- deterministic semantic fingerprint under a declared canonicalisation version;
- closed authority classes showing that no candidate, risk, capital, execution or lifecycle authority is granted.

Projection time must derive from explicit source/effective/as-of facts. Current wall-clock time, capture time, packet emission time or a caller default must not replace missing source temporal authority. Date-only truth remains date-only.

### 7.9.6 Lawful absence, persistence and side-effect boundary

Missing authority and valid absence are different states:

- missing mandatory Market Session Reference truth for the target scope withholds the authoritative projection;
- unavailable or unproven Financial Event Reference completeness is `unknown`, not `no events`;
- unavailable operational state may support a reference-only degraded projection only where the policy expressly admits that mode;
- a valid complete search yielding no relevant event facts may report an empty result only with the searched scope/window and completeness evidence;
- unresolved mandatory conflict withholds the affected projection.

Reference snapshots are immutable selected authority. Operational corrections are append-preserved facts with explicit supersession lineage; duplicate identity or contradictory reuse fails closed. Derived projections are transient immutable outputs unless an owning persistence contract explicitly retains them. Any M13 transaction participation covers atomic storage mechanics only and does not transfer M02 semantic ownership.

M02 projection is side-effect-free. It must not fetch live providers, mutate reference or operational state, create candidates, decide posture/risk/capital, construct orders, mutate positions, perform lifecycle action or claim replay authority.


## 7.10 M03 K05 Prepared Data Envelope and K06 Field Resolution Receipt law

This section closes the positive architecture obligations identified as contracts `K05` and `K06` and requirements `C-008`, `C-011`, `C-012` and the M03 share of `C-015`. It governs only typed runtime preparation, canonical field resolution, deterministic derivation evidence and explicit enrichment gaps. It does not admit source acquisition, calendar rewriting, stage cognition, risk, capital, packet identity, execution, position, lifecycle or replay authority.

### 7.10.1 Canonical public contracts and ownership

M03 owns three public contracts:

1. `PreparedDataEnvelope` — one immutable, versioned K05 prepared-data authority envelope carrying common identity, source/capture lineage, temporal facts, policy/schema/derivation versions, fingerprints, validation/completeness state and exactly one tagged typed payload variant;
2. `FieldResolutionReceipt` — one immutable K06 receipt preserving all admitted candidates and the deterministic selected, coalesced, unavailable, degraded or withheld outcome for one semantic field under one versioned rule; and
3. `PreparedDataBuilder` — the side-effect-free M03 service that validates admitted M01/M02 inputs, executes explicit field-resolution and derivation law, and emits a `PreparedDataEnvelope` or an explicit non-emission failure.

M01 owns source identity, capture identity, source contracts and source temporal truth. M02 owns calendar facts and projections. Resolution must obey this order:

3. select one unequal candidate only through the policy's named owner or lawful bounded fallback rule, recording every rejected candidate and reason;
