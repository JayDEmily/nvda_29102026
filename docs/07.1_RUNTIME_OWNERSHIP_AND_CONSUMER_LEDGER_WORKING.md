## 7.1 Alpha ownership and state-authority model

The core one-owner/one-meaning rule governs semantic ownership. This overlay adds the alpha-stage distinctions needed to prevent an implementation file, repository interface, packet, receipt, or review surface from silently becoming authority for a different question.

For every material output or state domain, the architecture must distinguish these roles where they apply:

- **semantic owner** — defines the bounded meaning, invariants, and lawful decisions of the output or state;
- **authorised emitter or state writer** — is the only bounded component permitted to originate the material output or mutate the owned state;
- **coordinator** — may sequence calls and carry results but does not acquire the semantic authority of the components it coordinates;
- **persistence owner** — defines the repository or store boundary, duplicate/update law, and readback contract for retained state;
- **reader or consumer** — reads through the declared carrier, query, repository, or store contract and must not infer authority from internal representation;
- **review or explanation owner** — may describe preserved outputs and limitations but must not rewrite the decisions or state it reviews.

A Python module, class, service, endpoint, test, or receipt path is implementation evidence or a target allocation. Its location does not by itself create normative ownership, prove that the target owner is correctly implemented, or prove that the state is durable.

## 7.2 Required ownership record

Before a material boundary can be called aligned, its ownership record must state, at minimum:

1. architecture surface and bounded question answered;
2. semantic owner;
3. authorised emitter or state writer;
4. lawful readers and downstream consumers;
5. input and output carrier or contract;
6. material identifier owners and propagation obligations;
7. structural status and implementation-truth status;
8. current state-retention class and concrete implementation truth;
9. duplicate, update, append, or replacement rule where state exists;
10. minimum facts required for governed re-execution and preserved-envelope evidence;
11. required-absence and fail-closed behaviour;
12. forbidden authority mixing;
13. replacement or extension boundary;
14. direct evidence and unresolved `Unknowns`.

This record is semantic architecture law. Gate B must populate it boundary by boundary through full reading of the applicable contracts, tests, code, configuration, and state surfaces. A generated inventory or matching field name cannot establish any of these answers.

## 7.3 Alpha state-retention truth

Current state must be described by what the concrete implementation actually retains:

- a derived output that is not retained beyond the call is transient;
- a list, dictionary, singleton, module global, or object-held repository that disappears on process termination is process-memory state and is non-durable;
- checked-in configuration or reference material is repository-versioned input, not runtime state merely because runtime code reads it;
- a receipt or artefact written to a file is file-retained only to the extent proved by the actual write and readback path;
- state is database-backed only where the active path writes and reads that state through the declared database boundary;
- a placeholder or reserved surface has no current material state authority beyond the explicitly admitted shell or specimen behaviour.

A repository contract may define the future durable boundary while its current alpha implementation remains process-memory and non-durable. JSON serialisability, copy-on-read, duplicate rejection, append-only behaviour, an ORM dependency, a migration tool, or a database driver does not independently prove restart survival.

This alpha classification does not choose production storage technology, retention periods, backup policy, recovery objectives, deployment topology, capacity, or availability requirements. Those remain outside current authority.

## 7.4 Minimum replay envelope

For every material deterministic decision or state transition, the owning boundary must identify the minimum logical facts needed to explain and, where claimed, re-execute that result. The applicable typed contracts must preserve or reference:

- authoritative source or captured-input identities and fingerprints;
- input contract and schema versions;
- source observation or effective time facts, distinct from process emission time;
- material configuration, policy, coefficient, playbook, and algorithm/module versions that can change the result;
- upstream decision, packet, receipt, and state-snapshot identities actually consumed;
- the bounded output or transition identity;
- deterministic semantic result fingerprint where the domain supports one;
- explicit missing, optional, blocked, or non-applicable facts;
- original packet or receipt identity when preserved-envelope evidence is claimed.

The exact field names and per-boundary mandatory subset remain to be fixed during the Gate B semantic walk. The system must not fabricate missing facts, treat a new packet as the original envelope, or describe a locally deterministic function as end-to-end replay proof.

## 7.5 Writer, reader, and substitution law

Only the authorised writer may originate or mutate the truth owned by a material state domain. A coordinator, API adapter, packet builder, review layer, test, or downstream consumer may carry, request, validate, or describe that truth only through its declared contract.

A reader must not access private repository representation, shared mutable objects, or implementation internals when a lawful read contract exists. A read model may differ from the write model, but it must preserve the owned meaning and identify its source state.

A concrete provider, repository, configuration source, audit sink, scheduler, user interface, playbook family, or policy implementation is replaceable only through its owning contract and explicit assembly or registration boundary. Replacement must not require unrelated domain owners to absorb provider-specific fields or implementation branches. This applies inside the modular monolith and does not require microservices, separate databases, dynamic plugin machinery, or distributed messaging.

## 7.7 M07 K12 coefficient/modifier bundle, decision and receipt law

This section closes the positive architecture obligation identified as contract `K12` and cohort decision `C-012` for module `M07`. It governs only coefficient and modifier authority. The word `policy` in `PolicyBundle` is therefore local to M07's bounded coefficient/modifier policies and must not be read as calendar, playbook, capital, execution, lifecycle, replay or global strategy authority.

### 7.7.1 Canonical public contracts and ownership

M07 owns three public contracts:

1. `PolicyBundle` — one immutable, versioned M07 coefficient/modifier authority bundle;
2. `ModifierDecision` — one deterministic, side-effect-free resolution result for a valid bundle and identified input-state facts;
3. `ModifierApplicationReceipt` — immutable evidence that one non-rejected decision was resolved for one owner stage and application context.

M07 owns bundle validation, coefficient/modifier identity, deterministic ordering, conflict resolution, hard-bound enforcement, resolution status and receipt meaning. It does not own the upstream facts used to determine whether a modifier is applicable. It must consume those facts through identified, versioned or fingerprinted owner contracts. It must not infer state from ungoverned strings, current wall-clock time, mutable globals, caller order or hidden runtime observation.

A `ModifierApplicationReceipt` records M07 resolution/application evidence only. It is not an M12 replay result, an M13 transaction receipt, a capital decision, a strategy-selection receipt or proof that a downstream owner mutated state.

### 7.7.2 PolicyBundle identity, version and member law

A valid `PolicyBundle` must declare, at minimum:

- `bundle_id`, `bundle_version`, `schema_version`, `authority_id` and `authority_version`;
- one explicit effective-version interval or equivalent promoted-version selector;
- an immutable coefficient-member collection and an immutable modifier-member collection;
- the bundle's deterministic resolution-law version;
- promotion/workbook lineage sufficient to identify the admitted authority source.

Bundle identity and version are inseparable. An unknown, missing, superseded-without-compatible-selection or schema-incompatible version fails closed. A caller may request a bundle by identity/version but may not construct an authoritative bundle by supplying an arbitrary mapping.

Each coefficient member must declare a unique coefficient identity and version, exact owner stage, value type and units, baseline value, hard lower and upper bounds, surface class, admitted transform family, runtime-mutability class and promotion/workbook lineage. Baseline and bounds must be finite and type-compatible; the baseline must lie inside the hard bounds. Any declared threshold ordering or asymmetric law is part of the member authority and must be validated before resolution.

Each modifier member must declare a unique modifier identity and version, exact target coefficient identities, the same lawful owner stage as those targets, explicit applicability fact references, precedence rank, transform operator and operand, compatibility/combination law, conflict or veto relations, and any kill-switch or restrictive-only status. A modifier may target only admitted mutable coefficient members. It may not create a new coefficient, widen a target's hard bounds, replace the owner stage, select a playbook, allocate capital or mutate an external state owner.

A bundle with no coefficient members is invalid. A valid bundle may contain no modifier members; that is an explicit no-modifier bundle, not a missing bundle.

### 7.7.3 Applicability, lawful absence and fail-closed outcomes

The following states are distinct:

- **missing or invalid bundle** — resolution is rejected; no binding effective values and no `ModifierApplicationReceipt` may be emitted;
- **valid bundle with no modifier members** — resolution is a valid no-op preserving every baseline;
- **valid bundle with modifier members but none applicable** — resolution is a valid no-applicable-modifiers outcome preserving every baseline;
- **valid bundle with applicable modifiers** — deterministic precedence, conflict and bounds law applies.

Missing applicability facts are not equivalent to a false condition unless the owning fact contract explicitly defines that equivalence. An unavailable, stale, incompatible or unidentifiable material fact must reject or withhold the affected resolution rather than activate a modifier or silently use a default.

A rejected `ModifierDecision` may identify the requested bundle reference, owner stage and exact failed authority facts, but it must not fabricate a valid bundle identity, effective values or successful application. Only `applied`, `no_modifier_members` and `no_applicable_modifiers` decisions may produce a `ModifierApplicationReceipt`.

### 7.7.4 Deterministic precedence and conflict law

For a valid bundle and complete admitted input facts, M07 must:

1. validate unique member identities, versions, owner stages, targets, types, bounds and transform families;
2. evaluate applicability only from the declared input-fact references;
3. order applicable modifiers by authority-owned precedence, not by caller or container order;
4. apply explicit compatibility/combination law for modifiers sharing a target;
5. make a hard kill switch, hard block or explicit veto dominate weaker scaling or permissive effects;
6. preserve the most restrictive categorical block where several compatible restrictions apply;
7. reject equal-precedence or otherwise unresolved incompatible effects rather than choose arbitrarily;
8. perform admitted bounded algebra in the resolved order;
9. clamp the numeric candidate to the coefficient's hard bounds after bounded algebra and record whether and where clamping occurred.

A stable identity/version tie-break may be used only where the bundle expressly declares the effects compatible and commutative or declares that tie-break as part of the resolution law. Sorting by identity must never conceal a semantic conflict. Boolean, categorical and enumerated surfaces require explicit operator law and must not be coerced through numeric algebra.

No resolution may increase authority beyond the bundle. In particular, M07 cannot use a modifier to open fresh capital, bypass an upstream hard block, widen a coefficient hard bound or convert an unavailable owner fact into permission.

### 7.7.5 ModifierDecision minimum facts

A non-rejected `ModifierDecision` must preserve or reference, at minimum:

- decision identity and deterministic semantic fingerprint;
- bundle, authority, schema and resolution-law identities/versions;
- owner stage and identified input-state/context identity, version, effective time and fingerprint;
- decision status;
- ordered evaluated, applied and skipped modifier identities/versions with exact reasons;
- per-coefficient baseline, pre-clamp candidate, hard bounds, effective value and bound disposition;
- any applicable veto, kill-switch, restriction or conflict disposition;
- closed authority classes showing that capital, playbook, execution, lifecycle and replay authority were not acquired.

The semantic fingerprint must include every material fact that can change the decision and must exclude occurrence-only metadata such as receipt emission time or a random receipt identifier. The same exact bundle/version, resolution-law version and admitted input facts must produce the same semantic decision and fingerprint.

### 7.7.6 ModifierApplicationReceipt minimum facts and side-effect boundary

A `ModifierApplicationReceipt` must preserve or reference, at minimum:

- receipt identity, application identity and source `ModifierDecision` identity/fingerprint;
- bundle, authority, schema and resolution-law identities/versions;
- owner stage and input-state/context identity, version, effective time and fingerprint;
- decision status and the ordered modifier/application facts that produced it;
- per-coefficient baseline, candidate, bounds, effective value and clamp disposition;
- explicit no-op class when no modifier member exists or none is applicable;
- closed authority classes and any limitations;
- receipt emission time, separately labelled as occurrence metadata.

M07 resolution is side-effect-free. A lawful downstream owner may consume a non-rejected decision and mutate only its own state under its own contract. The receipt may attest that the decision was presented to or resolved for that owner-stage context, but it must not claim that an external mutation occurred unless an owner-specific atomic receipt separately proves it.

M12 may later replay or compare M07 evidence using the exact bundle/version, resolution-law version and input facts. That downstream use does not transfer replay authority to M07 and does not permit current code, current configuration or wall-clock state to stand in for the original material set.

## ROADMAP_5_16_PERSISTENCE_LEDGER_RECEIPT_HARDENING_001

Status: retained admitted ownership supplement for row `5.16 Persistence, ledgers, and receipts`. It does not assert current implementation maturity or current mutation authority.

The persistence hardening tranche adds these local ownership rules:

1. A concrete repository implementation that is lawfully classified as storing durable truth by identifier must reject duplicate identifiers instead of silently overwriting earlier truth.
2. A repository that stores append-only observations or records must preserve insertion order and must not expose keyed overwrite/upsert methods unless a later tranche admits reconciliation policy.
3. All persistence readback and list surfaces must return copies, not mutable internal storage.
4. The receipt ledger owns audit/checkpoint receipts only. It does not own trading decisions, capital/risk judgement, source-data truth, or Atlas admission state.
5. Receipt payloads admitted by the native receipt ledger must be JSON-serialisable so they can be written, read, diffed, and checked by later proof tooling. JSON serialisability alone does not establish durable storage, original-envelope preservation, or replay completeness.
6. Compatibility wrappers may re-export the benchmark-owned persistence home, but wrappers must not become a second writer of durable truth.

The overlay opens no live broker, order, position-sizing, capital-deployment, or risk-weighting behaviour.
