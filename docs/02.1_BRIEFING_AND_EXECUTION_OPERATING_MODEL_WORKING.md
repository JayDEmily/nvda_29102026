# 02.1_BRIEFING_AND_EXECUTION_OPERATING_MODEL_WORKING

All repo paths in the numbered control stack are repo-root-relative.

## Status

This working overlay contains an admitted alpha-stage clarification and extension of `docs/02_BRIEFING_AND_EXECUTION_OPERATING_MODEL_CORE.md`.

The core operating sequence and separation of candidate formation, independent risk assessment, downstream blocking, capital deployment, opening, execution-state feedback, inventory/close, and review remain binding.

## 2.1 Target operating model versus current alpha implementation

The ordered fourteen-step sequence in the core is the required complete-run operating model.

It is not a claim that the current alpha code executes every step end to end, consumes live or paper market data, or has production-ready downstream behaviour.

Current implementation truth must be stated separately for each architecture surface using the status model in `docs/11_NATIVE_ARCHITECTURE_BLUEPRINT_CORE.md`.

A bounded component or stage may be exercised independently during alpha development. That exercise must not be described as a complete governed run unless every required step is present, connected through lawful carriers, and proved in order.

Where a required step is absent, reserved, placeholder-only, or unable to establish required authority, a complete-run entry point must fail closed or stand down. It must not skip the step, fabricate its output, or silently substitute an adjacent output.

## 2.2 Stable sequence and replaceable implementation rule

The behavioural sequence is stable. Implementations inside its bounded parts must remain replaceable at known future-change boundaries.

A change to an external input provider, input type, playbook, coefficient policy, risk policy, persistence implementation, execution adapter, or review presentation must not require unrelated stages to absorb that implementation's internal rules.

Replaceability requires:

1. one bounded owner for the variable capability;
2. an explicit input and output contract;
3. selection or configuration outside unrelated stage logic;
4. no hard-coded dependency on a fixed number of implementations;
5. no hidden imports or shared mutable state across the boundary;
6. tests that prove both the contract and lawful substitution;
7. an honest alpha implementation status.

This rule does not require microservices, distributed infrastructure, a plugin framework, or speculative abstraction. A modular monolith with explicit contracts is lawful.

## 2.3 Playbook expansion rule

The playbook library owns governed playbook definitions and selection metadata.

The serial playbook-eligibility stage consumes the library through an explicit registry or equivalent governed contract. It must not own the internal implementation of every playbook.

Adding, removing, or replacing a playbook must ordinarily require changes only to:

- the playbook-owned definition or implementation;
- its registration/configuration material;
- its playbook-specific tests and fixtures;
- any explicit normative admission required for a genuinely new playbook meaning.

It must not ordinarily require changes to temporal context, market regime context, options and flow context, posture and risk permission, downstream capital deployment, live inventory, or unrelated playbooks.

The orchestrator and eligibility stage must not encode the assumption that the library contains four playbooks, ten playbooks, or any other fixed count.

A playbook definition or registry entry may affect candidate formation only through the playbook library and eligibility contracts. It must not carry hidden capital, broker, exit/close, persistence, or coefficient authority.

## 2.4 Meaning of serial “expression and execution”

Within the serial desk-cognition spine, `expression and execution` means formation of the candidate's execution expression, lifecycle intent, and bounded handoff material.

It does not mean:

- broker order submission;
- external API execution;
- placement readiness;
- execution receipt or fill-state authority;
- live inventory mutation;
- exit or close execution.

Those behaviours remain downstream and must use their separately governed owners and carriers.

The serial stage must therefore emit candidate material that can be consumed downstream without pretending that placement or execution has occurred.

## 2.5 Extension does not alter the sequence by implication

A new input family, playbook, policy, adapter, persistence implementation, or review view does not create a new governed runtime step merely because it is new.

It must be allocated inside an existing bounded owner or be explicitly admitted as a normative sequence change.

Likewise, replaceable implementations inside a step do not permit the step to be skipped, merged, reordered, or allowed to take over another step's authority.
