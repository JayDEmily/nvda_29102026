# 08.1_TESTING_AND_PROMOTION_WORKING

All repo paths in the numbered control stack are repo-root-relative.

## Operative status and relationship to the core

This working companion adds alpha-stage testing, proof-claim, isolation, traceability, and promotion clarifications to `docs/08_TESTING_AND_PROMOTION_CORE.md`. It does not weaken the core proof tiers or create production-readiness requirements.

The core remains authoritative except where this companion makes an ambiguity explicit. Tests, proof manifests, registries, commands, receipts, and green results remain downstream evidence. They do not create normative intent, semantic ownership, implementation maturity, or permission to change a governed surface.

## 8.1 Alpha proof-claim law

A passing test or proof block proves only the exact proposition exercised by its assertions under the recorded environment, inputs, fixtures, dependencies, and state. It does not prove adjacent behaviour, end-to-end composition, persistence, replay, production readiness, or architectural conformance that the test did not exercise.

Every material proof claim must state:

1. the normative proposition or bounded architecture claim being tested;
2. the target surface and current structural and implementation-truth status;
3. the test level and boundaries actually exercised;
4. the authoritative inputs, fixtures, state and dependency substitutions used;
5. the expected positive and negative outcomes;
6. the failure signal;
7. the environment and command used;
8. the limitations and unproved adjacent claims.

A large count of passing component tests cannot substitute for a missing integration, contract, state-readback, restart, or end-to-end test where the claimed behaviour crosses those boundaries.

## 8.2 Normative proposition traceability

Tests are derived from accepted normative propositions. Current code behaviour, existing test assertions, proof-block membership, receipts, or historical green status must not be reverse-promoted into normative intent.

For every blocking proof family, the proof register must identify the exact normative proposition or propositions it validates. A reference to an entire document is insufficient where the document contains multiple independent requirements.

A normative proposition may require more than one test family. A test family may validate more than one proposition only when each relationship is explicit and the assertions genuinely exercise each proposition.

When a normative proposition changes, its linked tests become suspect until they are semantically reviewed and either confirmed, amended, replaced, demoted, or retired. Automated path matching or keyword similarity cannot establish this traceability.

## 8.3 Proof-family adequacy

Gate C must select the smallest combination of proof levels that can establish the accepted claim. Where applicable, that combination includes:

- focused deterministic component tests for bounded algorithms and invariants;
- contract tests for typed carriers and producer/consumer expectations;
- integration tests for interactions across real owner boundaries;
- state tests for duplicate, update, append, readback, copy-safety and restart behaviour actually claimed;
- sequential or end-to-end tests only when the claimed lifecycle crosses the whole path;
- replay tests that provide the authoritative inputs and material versions required by the governing replay envelope.

For each material rule, tests must cover the relevant forms of:

- lawful positive behaviour;
- prohibited or false-positive behaviour;
- missing mandatory authority and lawful optional absence;
- identifier and lineage preservation;
- extension or substitution at a declared volatility boundary;
- deterministic equivalence where determinism is claimed;
- status preservation for provisional, placeholder, reserved, and future-only surfaces.

Coverage percentage, assertion count, test count, file presence, import success, schema construction, or manifest registration is not semantic proof of a requirement by itself.

## 8.4 Proof applicability is not architecture ownership

The `owns` field currently used by `config/proof_blocks.yaml` means that the block is declared applicable to the listed proof and implementation surfaces for proof selection and path-existence validation. It does not grant the proof block, test, registry, or runner:

- semantic ownership of those surfaces;
- mutation authority over those surfaces;
- authority to redefine their contracts;
- authority to promote their implementation status;
- proof that every listed surface is exercised by the command.

Gate C must reconcile this field into an unambiguous proof-applicability model. Until then, `owns` must be interpreted narrowly as historical applicability metadata and must not be cited as implementation or architecture ownership.

Proof tier and lifecycle labels must be schema-valid, explicitly admitted, and consistent across the proof manifest, retained-test registry, current normative proposition register, commands, and receipts. A string labelled `Tier A` does not become blocking authority merely because it exists in a manifest.

## 8.5 Test isolation and governed-artefact law

A checking or promotion command must be repeatable from the same governed starting state and must not depend on another test leaving state behind. Tests must establish and clean up their own temporary state.

A read-only proof command must not modify tracked source, normative documents, configuration, fixtures, canonical data, candidate registers, ledgers, or other governed evidence. If a workflow legitimately generates or updates a governed artefact, generation and checking must be separate commands with separate authority:

- generation requires an explicitly authorised mutation gate and records the intended diff;
- checking reads the governed artefact without changing it;
- temporary outputs are written outside tracked governed paths or are removed before the command completes;
- pre-run and post-run Git state is inspected for promotion evidence.

A proof command that unexpectedly changes tracked truth fails proof isolation even when its assertions pass.

## 8.6 Declared-environment closure

The canonical declared environment must be sufficient to collect and execute every proof family admitted to the current promotion set. Every direct runtime or test dependency needed by that set must be declared through the repository packaging authority and reproducibly installed through the canonical flow.

A package installed manually, inherited from an operator environment, or supplied only by an audit workaround does not satisfy environment provenance. The presence of an import in a Tier A test creates a dependency decision that must be resolved through declared authority before that test can support promotion.

This rule governs reproducibility only. It does not require production deployment, container, cloud, availability, backup, or recovery architecture during alpha.

## 8.7 Authoritative aggregate promotion gate

The repository must define one authoritative aggregate command or manifest-resolved procedure for the exact current promotion claim. It must:

1. identify the complete admitted Tier A set for the touched and dependent propositions;
2. validate proof-block and retained-test registry consistency;
3. execute, rather than merely enumerate, the blocking commands;
4. fail when any admitted blocker is red, missing, skipped without authority, or unreconciled;
5. record environment provenance and exact command results;
6. inspect pre-run and post-run Git state;
7. distinguish targeted development feedback from promotion evidence.

A targeted Make target, selected proof block, manifest structure check, local test slice, or mostly green full suite is not the aggregate promotion gate unless current live doctrine explicitly defines it as such and it includes every admitted blocker for the claim.

The aggregate gate may remain provisional until Gate C reconciles the proof model. Until then, no existing command is inferred to be the complete promotion authority merely because it is convenient or green.

## 8.8 Status preservation and meaning of promotion in alpha

In this alpha project, promotion means accepting a bounded branch or architecture claim into the next governed repository state. It does not mean production deployment, live trading readiness, operational resilience, or fitness for capital use.

Tests for a `thin_seam`, `placeholder`, `reserved`, or `future_only` surface may prove only the bounded seam, rejection, shell, reservation, or non-participation rule that current normative authority permits. Passing tests must not upgrade that surface to `implemented` or authorise it in runtime composition.

An implementation-truth status changes only through the architecture baseline and its required evidence. Proof records the evidence for that decision; proof does not make the decision automatically.

## 8.9 Gate C transition rule

Gate A establishes testing law but does not repair tests, dependencies, proof manifests, registries, runners, Make targets, or source code. Gate B determines the exact normative-to-test-to-code gap for each sequential boundary. Gate C then creates or repairs the smallest proof family for one accepted boundary at a time before Gate D changes implementation.

Known current proof defects remain explicit inputs to Gate C, including:

- declared-environment collection failure caused by an undeclared direct test dependency;
- read-only vocabulary proof commands that mutate a tracked governed candidate artefact;
- predominantly green proof that does not exercise fabricated-lineage and restart-durability prohibitions;
- selected validation commands that omit an admitted failing blocker;
- proof applicability metadata whose name can be mistaken for semantic ownership.

Recording those defects here does not repair or waive them.

## 8.10 Machine-enforced proof-control propositions

The following proposition identifiers are stable control locators for M14 proof-promotion tooling. They govern admission and promotion mechanics only; they do not create module-domain meaning.

- **`TP-ADMISSION-001` — Exact path admission.** Every physical `test_*.py` file under `tests/tier_a`, `tests/tier_b`, or `tests/tier_c` must have exactly one machine-readable family and lifecycle disposition. Physical folder placement, a historical registry row, a proof-block command, or a receipt cannot silently admit the file.
- **`TP-SELECTION-001` — Registry-derived selection.** A current proof block selects tests only through admitted test-family identifiers in the retained-test registry. Its executable test-path membership must resolve exactly to those families; an independent path list cannot become a second admission authority.
- **`TP-TRACE-001` — Exact normative traceability.** Every current blocking family and every block in a current promotion set must cite one or more exact accepted normative proposition identifiers or locators. Whole-document references, architecture allocation, historical green state, or test names alone are insufficient.
- **`TP-PROMOTION-001` — One aggregate gate.** Each current promotion claim has one named manifest-resolved set and one repository-owned command that validates authority, resolves the complete membership, executes every blocker and fails closed on missing, red, skipped, timed-out, collection-failed or unreconciled proof.
- **`TP-RECEIPT-001` — Sufficient promotion receipt.** Aggregate promotion evidence records the Git commit and branch, pre-run and post-run governed state, interpreter and platform, lock and authority-file identities, resolved family/block/test membership, exact commands, per-block outcomes, counts, duration and a deterministic evidence hash.
- **`TP-ENV-001` — Declared installed environment.** The canonical install route consumes the repository lock authority, and at least one promotion smoke path imports the installed package without relying on repository-root or `src` path injection that can mask packaging defects.
- **`TP-CONTROL-001` — Single active control state.** Canonical plan, live roadmap and active process overlay must agree on one current control pack and gate. Legacy, expected-red, compatibility and historical proof remain visible but cannot conflict with or silently enter the current green promotion claim.

A schema or command that merely parses its own file does not satisfy these propositions. The two authorities must be reconciled together, and executable membership must be derived from that reconciliation.
