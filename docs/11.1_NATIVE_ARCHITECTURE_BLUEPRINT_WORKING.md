## 11.4 Modularity and future-change law

Future-proofing means that a known changing implementation can be added, replaced or removed through one explicit owned boundary without rewriting unrelated domains. It does not mean predicting every future requirement or creating a generic plugin framework before a real boundary exists.

The following volatility points are already known and must remain replaceable:

- external providers and source formats through adapters plus versioned typed input contracts;
- raw input families through owned typed family contracts and a controlled registration/configuration boundary;
- playbook and strategy definitions through a playbook contract and registry, with orchestration consuming the contract rather than strategy internals;
- coefficient and modifier policies through governed configuration and bounded policy contracts;
- risk policies through owned policy/service boundaries rather than module-global mutable state;
- persistence technology through repository/store contracts and an explicit composition root;
- broker or simulated-execution implementations through downstream contracts and adapters;
- review/export representations through read-only projections over preserved authoritative evidence.

Adding a fifth or tenth playbook must not require rewriting the runtime orchestrator, API composition, persistence implementations, unrelated playbooks or downstream state owners. A new playbook may require a new implementation, semantic vocabulary admission, registry/configuration entry and its own proof, but the stable playbook consumer contract must remain unchanged unless the contract itself is lawfully versioned.

A common envelope or base interface must preserve strong typed payload contracts. Extensibility must not be achieved by moving domain meaning into ungoverned dictionaries, opaque extension blobs, string dispatch or broad `Any` values.

No microservice, message broker, dynamic plugin loader, service mesh, cloud deployment surface or distributed state mechanism is required by this alpha architecture. The modular monolith remains the target form unless an actual ownership, scaling, isolation or deployment requirement later justifies separation.

## 11.5 Component, ownership and composition boundaries

The core component-form table remains binding. The following clarifications apply:

- an API route or entry point owns transport handling and composition only; it must not become the semantic owner of domain mapping, persistence truth or identifier creation;
- an orchestrator owns order and coordination only; it consumes owned stage contracts and must not contain hidden stage, strategy, risk or capital policy;
- a registry owns lawful lookup and selection metadata only; it must not become an untyped global service locator;
- a repository or store owns state access for one named state domain; it must not own the domain decision that creates the state;
- a contract or packet owns shape and invariants only; it must not manufacture upstream authority or execute domain logic;
- a service may implement one bounded domain action but must receive infrastructure dependencies through explicit construction or a lawful composition root.

Semantic ownership, authorised writing, coordination, reading and review are separate responsibilities under `docs/07_RUNTIME_OWNERSHIP_AND_CONSUMER_LEDGER_CORE.md` and its working addendum. File placement or a class name does not by itself prove ownership.

The current `src/nvda_desk/api/app.py` composition concentration, direct/private state access and process-global risk state are implementation gaps, not accepted blueprint patterns.

## 11.6 Persistence and alpha technology direction

The current declared dependency set supports SQLAlchemy and PostgreSQL-capable drivers. Current source also contains bounded SQLite-backed persistence. This is present technical direction, not a production database decision.

At alpha stage:

- in-memory repositories are lawful only when explicitly labelled non-durable and kept behind the same bounded contract expected of a later persistent implementation;
- SQL-backed stores may prove a bounded persistence seam without establishing that every material state domain is durable;
- each material state domain must name its semantic owner, authorised writer, readers, current implementation, current durability status and minimum replay evidence during Gate B;
- production retention, backup, recovery objectives, high availability, capacity and deployment constraints remain outside current authority.

Persistence technology must not leak into domain algorithms or require unrelated domain changes when a repository implementation changes.

## 11.8 Deterministic non-AI scope

The present NVDA runtime is deterministic code and algorithms. No language-model, agent, tool-calling, handoff, prompt, model-provider or agent-tracing runtime is authorised or implemented.

OpenAI agent architecture guidance therefore does not define current runtime structure. Importing agent, handoff, prompt or model abstractions into the deterministic domain would be speculative and is prohibited.

If a future user-approved model or agent capability is introduced, it requires a new normative addendum that defines its bounded purpose, typed inputs/outputs, model/provider configuration authority, deterministic fallback or stand-down behaviour, tracing/privacy boundary, evaluation proof and prohibition from silently acquiring trading, risk, capital or persistence authority.

### 11.10.2 Progressive package migration

The target physical namespace is `src/nvda_desk/mxx_module_name/`. Migration is progressive:

- create a package only when its module becomes active;
- move, refactor or replace only the active ownership boundary;
- expose one explicit public package API;
- direct temporary compatibility adapters toward the target owner;
- add no new domain behaviour to superseded locations;
- remove compatibility paths only after consumers migrate and proof passes;
- run dependency and cycle checks after each module.

The module ID belongs at package and architectural boundaries. Local variables, private helpers and non-exported implementation details remain module-local vocabulary and do not require an `Mxx` symbol prefix.

The present source package graph contains two known small cycles, `contracts ↔ packets` and `cognition ↔ domain`. They are implementation defects to eliminate during the relevant module migrations; they do not alter the accepted acyclic target graph.

### 11.10.4 Parallel delivery boundary

A Parallel Execution Lane is capacity, not module ownership or a long-lived branch. Each Lane Assignment uses one fresh worker branch and one independent tester thread from a named canonical checkpoint. A Lane Assignment cannot mutate another module's contract, a shared proof or vocabulary registry, root configuration, composition wiring or global project-control state unless the PM opens an exclusive integration unit.

Workers and testers may overlap in time. The PM imports approved results sequentially, reruns affected proof and publishes one combined checkpoint. A tester PASS returns a Tester-approved Portability Artefact suitable for PM integration review; it does not alter canonical architecture, authority or implementation status.

### 11.10.5 Proof relationship

The module architecture does not waive the direction normative authority → truthful proof → implementation. Gate C now applies that sequence locally to the active module. Unrelated unreviewed tests remain visible as `LEGACY_SHADOW_UNADMITTED` and cannot dictate the active implementation merely because they pass or fail. Final whole-system reconciliation remains mandatory before any end-to-end or production-readiness claim.
