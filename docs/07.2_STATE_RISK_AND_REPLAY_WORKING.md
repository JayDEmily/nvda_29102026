## 07.2.N06 Smallest admitted transaction boundary

### 07.2.N06.1 Transaction unit

The smallest admitted transaction boundary is one accepted domain command or decision together with every repository mutation and receipt/commit record required to truthfully claim that command's result for its declared consistency unit.

The consistency unit must be named by the owning domain contract. It is normally one aggregate or one explicitly coupled set of state records whose invariants cannot be truthful if committed independently. It is not a repository-wide global transaction and it must not absorb unrelated domains merely for implementation convenience.

Examples of transaction-unit classes include one accepted capital-authority decision and its owned capital state/receipt, one placement acceptance and its order-intent/execution-attempt records, or one inventory reconciliation and its position-state/receipt changes. These examples identify boundary form only; they do not authorise production actions or concrete schemas.

### 07.2.N06.2 Declared participants and invariants

Before execution, the transaction contract must declare:

- command/decision identity and idempotency key;
- input semantic fingerprint and owning policy/config versions;
- consistency-unit or aggregate identity;
- expected prior state version or sequence where concurrency matters;
- every state repository/stream that must change;
- the receipt, event or commit record that will attest the result;
- invariants that must hold before and after commit; and
- deterministic success, duplicate, conflict and failure outcomes.

A receipt may describe only mutations included in the same admitted transaction or in a proven atomic commit/outbox mechanism. It must not claim that a position, capital balance, execution record or other material state changed merely because a separate append succeeded.

### 07.2.N06.3 Atomicity and failure truth

All declared state changes and the attesting receipt/commit record must become visible atomically at the admitted boundary. If any mandatory validation, optimistic-version check, mutation or receipt write fails, none of the declared changes may be presented as committed.

The failure outcome must preserve enough bounded evidence to diagnose the attempt without emitting a success receipt. A failed transaction may have an attempt/failure record only when that record is explicitly non-committing and cannot be mistaken for proof of the domain result.

Where an external irreversible side effect cannot participate in the local transaction, the system must use an explicitly governed prepare/commit, transactional outbox, acknowledgement or compensation protocol. Until that protocol proves the external result and local state consistency, the outcome must remain pending/uncertain rather than committed.

### 07.2.N06.4 Idempotency, duplicates and sequencing

The idempotency key is scoped to the named command type and consistency unit. The transaction must persist or otherwise atomically bind the key to the input fingerprint, result identity, resulting state version/sequence and receipt.

A repeated request with the same idempotency key and the same semantic input fingerprint must return the original committed result or receipt without repeating mutations or external effects. Reuse of the same key with a different semantic input fingerprint must fail as an idempotency conflict.

Receipts and state transitions must carry a deterministic sequence or version within the owning aggregate/stream. Insertion order in one process is not sufficient sequencing authority. Consumers must be able to distinguish committed order, duplicate replay and gaps.

### 07.2.N06.5 Cross-domain composition

Independent domain transactions remain independent. A workflow spanning capital, placement, execution and inventory is a sequence of owner-specific transactions linked by identities and state-machine status, not one invented global atomic operation.

A later transaction may begin only from an admitted prior committed result. If a later transaction fails, earlier committed domain truth is not rewritten; the workflow records the new failure/pending/compensation state under its owner. Receipts link the sequence but do not merge ownership.

### 07.2.N06.6 Persistence, substitution and replay

Repository interfaces used inside a transaction must expose transaction participation, expected-version enforcement and idempotent commit semantics required by the owner contract. A memory adapter may prove interface and in-process atomic behaviour, but it must remain labelled non-durable and cannot prove restart recovery, crash atomicity or external-effect reconciliation.

A future durable adapter may replace a memory adapter only if the same transaction contract tests run against it and prove atomic visibility, rollback/failure truth, duplicate replay, conflicting-key rejection, sequencing and restart recovery where claimed.

Authoritative replay must retain the command identity, idempotency binding, prior and resulting state versions, policy/config versions, mutations/events and committed receipt. Replay may reconstruct the transition but must not issue live external side effects.

### 07.2.N06.7 Current alpha consequence

Current receipt and execution-record stores are append-oriented, copy-safe in places and useful as alpha seams. They are independent in-memory collections: receipt IDs are duplicate-protected only in one ledger, execution records lack keyed idempotency, and neither surface is atomically bound to material capital, position or execution state changes.

That is a non-conforming implementation consequence only. No production source, runtime configuration, schema, fixture, migration or external action is authorised here.

## 07.2.N08 Serial/parallel final-risk join

### 07.2.N08.1 Purpose and required inputs

The final-risk join is the first and only boundary that combines the completed serial candidate/execution-expression risk state with the independent Parallel Risk Lane product. Its purpose is to decide whether the combined material is eligible to proceed to capital assessment or must stand down. It does not size capital, create orders, mutate the serial candidate or rewrite the Parallel Risk Lane assessment.

A valid join requires:

- serial candidate identity and semantic fingerprint;
- execution-expression identity and policy/version lineage;
- the serial permission/risk state, including every hard block and caution/constraint that remains active;
- Parallel Risk Lane packet identity, input/parent/dependency lineage, policy/config version and semantic fingerprint;
- every Parallel Risk hard block, caution, evidence-quality limitation and unavailable/unknown state; and
- final-join policy version and join-receipt identity.

The two input branches are independently mandatory. One branch must not be reconstructed from, substituted for or inferred from the other.

### 07.2.N08.2 Output and authority limit

The final join emits one immutable `final risk join receipt` with exactly one bounded action:

- `eligible_for_capital_assessment`; or
- `stand_down`.

The receipt must preserve all hard-block reasons, caution/constraint reasons, missing-authority reasons, branch identities/versions/fingerprints, join-policy version, deterministic output fingerprint and a clear statement that no capital sizing or execution authority is granted.

`eligible_for_capital_assessment` means only that both required branches are present and no active hard block prevents later capital assessment. It is not permission to trade and does not require capital authority to deploy.

### 07.2.N08.3 Precedence law

Precedence is conjunctive and fail-closed:

1. missing, invalid, stale-beyond-policy, contradictory or lineage-incomplete serial or Parallel Risk authority -> `stand_down`;
2. any active serial hard block or non-permission -> `stand_down`;
3. any active Parallel Risk hard block -> `stand_down`;
4. otherwise, active serial or Parallel Risk cautions/constraints are retained in full and the result may be `eligible_for_capital_assessment` only under the join policy; and
5. only two complete branches with no hard block can be eligible.

A caution is not positive authority. It cannot convert a missing or blocked branch into eligibility, erase another caution, raise confidence, or authorise capital. A clear branch cannot override the other branch's hard block. Numeric confidence or score must not dominate a categorical hard block.

Where a caution means later capital assessment is prohibited rather than merely constrained, that meaning must be explicit in the owning caution contract and the join policy; the final join must then stand down. The join must not invent that severity from wording or numeric magnitude.

### 07.2.N08.4 Independence and no hidden recomputation

The final join consumes the admitted outputs of the two owners. It must not:

- rerun serial cognition or Parallel Risk calculations;
- read raw/prepared signals not named in either branch;
- select playbooks, reform the candidate or alter execution expression;
- convert Parallel Risk into a serial stage or make it dependent on serial confidence;
- infer missing branch content from capital, inventory, API or review state; or
- collapse all reasons into one confidence scalar.

A new Parallel Risk atom/family or serial caution can be added behind its owning branch contract. The final join changes only when the cross-branch severity/precedence meaning genuinely changes.

### 07.2.N08.5 Conflict, duplication and replay

If the two branches contain contradictory identity, session, candidate or temporal lineage, the result is `stand_down` with explicit conflict reasons. Equal repeated reasons may be coalesced only while preserving both branch origins. Reasons with different owners or meanings must remain separate.

The join is deterministic for the same branch packets and join-policy version. Authoritative replay must retain or retrieve both exact branch products, their lineage and the join policy, and must reproduce the action, complete reasons/constraints and output fingerprint without current wall-clock or live state.

### 07.2.N08.6 Current alpha consequence

Current final-risk helpers inspect only whether the serial execution expression has a lead playbook, emit `continue`/`stand_down`, and convert that result into a scalar 1.0/0.0 receipt. They do not consume a Parallel Risk Lane packet, mandatory branch identity/version/fingerprint lineage, hard/caution semantics or conflict/missing-authority law.

That is a non-conforming placeholder consequence only. No production source, runtime configuration, schema, fixture or migration change is authorised here.

## 07.2.N09 Authoritative replay envelope

### 07.2.N09.1 Purpose and replay classes

Authoritative replay is a governed reconstruction or re-execution of a named material decision or state transition from retained authoritative evidence. It must establish what was consumed, which executable meaning applied, what state/order existed and whether the reproduced semantic result matches the retained original. Comparing two caller-supplied mappings is a subordinate analysis utility and is not authoritative replay.

The replay activity must declare exactly one class:

- `preserved_occurrence_replay`: re-delivery or inspection of the exact preserved packet, decision or receipt occurrence; the preserved occurrence identity remains unchanged;
- `governed_semantic_reexecution`: isolated re-execution from the exact retained logical inputs and versioned executable meaning; the replay run and every newly emitted packet/result receive new occurrence identities and reference the preserved originals; or
- `comparison_only`: deterministic comparison of supplied artefacts without a claim that the original governed decision was reconstructed.

A replay result must not blur those classes or call a newly emitted occurrence the preserved original.

### 07.2.N09.2 Minimum authoritative envelope

For a material decision or transition, the authoritative replay envelope must preserve or provide verified retrievable references to:

- replay-envelope identity, replay-run identity, declared replay class and target decision/transition identity;
- every authoritative source/capture artefact identity, content fingerprint and source/effective/observed/captured time fact actually consumed;
- dataset, symbol/session and bounded window identity where the decision depended on a data set or interval;
- input contract, schema, normalisation, preparation and projection versions;
- every material configuration, policy, coefficient, modifier, playbook, algorithm and executable module/version that could change the result;
- ordered upstream prepared envelopes, common contexts, stage carriers, packets, decisions, state snapshots, transaction/idempotency records and receipts actually consumed;
- every explicit missing, unavailable, degraded, blocked, conflict or non-applicable state presented to the original owner;
- the original bounded output/transition identity, reasons/constraints, semantic result fingerprint and attesting receipt; and
- deterministic ordering/version information sufficient to distinguish committed sequence, duplicate delivery and gaps.

For the propositions admitted in this controlled completion, the envelope must retain the N-02 calendar facts and supersession lineage, N-03 prepared envelope, N-04 field-resolution receipts, N-05 common context and stage carriers, N-06 transaction/idempotency/state-version evidence, N-07 phase evidence/history/policy and N-08 exact serial and Parallel Risk branch products plus final-join receipt wherever those facts were material to the target result.

A hash, packet ID, repository row, local object or fixture path is not sufficient by itself. The referenced content must be retrievable, type-valid and fingerprint-verified under the owning contract.

### 07.2.N09.3 Executable meaning and availability

A governed semantic re-execution requires the exact executable meaning that produced the original result to be retrievable or reproducibly addressable. That includes the applicable algorithm/module version and every result-changing policy/configuration dependency. Source revision alone is insufficient when generated artefacts, external packages or runtime configuration materially affect behaviour.

If any mandatory artefact, state version, ordering fact, contract/schema, policy/configuration dependency or executable version is unavailable, unverifiable or internally contradictory, the replay status is `non_authoritative_incomplete`. The system may still compare retained artefacts or explain the missing material, but it must not claim reconstruction, equivalence or deterministic end-to-end replay.

Production retention duration, storage technology, backup policy and recovery objectives remain Unknown. This authority defines the logical evidence that must exist for any replay claim; it does not invent operations policy.

### 07.2.N09.4 Isolated execution and side-effect prohibition

Governed semantic re-execution runs against isolated replay state, a controlled clock and retained source/effective time. It must not read current live provider data, current mutable production state or current wall-clock time as substitute authority. It must not place orders, mutate live capital/inventory/positions, write authoritative runtime state, acknowledge external effects or trigger any other live side effect.

Where the original transition involved an external effect, replay consumes the retained request, acknowledgement, reconciliation and compensation evidence. It does not repeat the effect.

Current emission time, replay-run identity and new packet occurrence identity may differ from the original and must be excluded from semantic domain-result equivalence. The replay result must retain explicit links to the original identities and distinguish transport duplication from new replay output.

### 07.2.N09.5 Deterministic result and authority assessment

For the same verified envelope and executable meaning, governed semantic re-execution must reproduce the original bounded semantic result, reasons/constraints, state transition and semantic fingerprint. The replay authority assessment must state:

- replay class and authority status;
- target and original-output identities;
- verified artefacts and versions consumed;
- missing, contradictory or unverifiable material;
- reproduced output identity and semantic fingerprint, where execution occurred;
- exact semantic matches and mismatches; and
- confirmation that no live side effect or runtime authority promotion occurred.

A semantic mismatch is evidence to investigate; it must not be normalised away, repaired by current data or overwritten by a comparison score. A match proves only the named bounded replay under the stated envelope and environment, not production durability, universal reproducibility or system-wide correctness.

### 07.2.N09.6 Comparison and extension law

Comparison utilities may deep-copy and diff two explicit artefacts, rank bounded analysis outputs or relate retained review citations to decisions. They remain `comparison_only` unless the authoritative envelope, executable availability, isolated re-execution and result-assessment requirements above are satisfied.

Adding a new source, state owner, policy family, packet role or decision stage changes replay through that owner's typed evidence/version contract and envelope contribution. It must not require the comparison utility to inspect private runtime repositories or invent generic mappings for unrelated domains.

### 07.2.N09.7 Current alpha consequence

Current replay surfaces can describe a fixture root, carry optional packet IDs/replay-run identity, compare arbitrary mappings and perform bounded review or walk-forward comparisons. They do not retrieve exact authoritative source/state artefacts, prove complete result-changing versions, reconstruct ordered transactions or execute an isolated original decision against a verified envelope.

Those surfaces are useful non-authoritative comparison and analysis seams. They are not end-to-end authoritative replay, and no production source, runtime configuration, schema, fixture, migration, persistence or retention change is authorised here.
