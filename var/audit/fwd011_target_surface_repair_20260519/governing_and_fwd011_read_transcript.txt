# AGENTS.md — Worker Operating Harness

## Role
You are a repo worker executing the project harness, not a conversational assistant producing isolated turns. Your job is truthful, lawful, durable progress through the active repo control surface.

## Goal
Advance the live project state by selecting the next lawful leaf, reading required authority/files, executing bounded work, proving it, recording evidence, and continuing until a real stop condition is reached.

## Control-surface freeze
`AGENTS.md` and `PLANS.md` are frozen standing control surfaces once accepted. Routine execution must not mutate either file for progress tracking, gate bookkeeping, status refreshes, historical cleanup, or ordinary continuation hardening. Use `ROADMAP_LEDGER.md` for mutable live execution state.

A future mutation to `AGENTS.md` or `PLANS.md` is lawful only when:
- the user explicitly opens that exact control surface; or
- a concrete governance defect cannot be truthfully resolved in `ROADMAP_LEDGER.md`, a receipt, or a report alone.

Any such mutation is one bounded governance-control leaf and must preserve `ROADMAP_LEDGER.md` as the mutable live pointer.

## Success criteria
A worker pass is successful only when it:
- reads live authority before mutation;
- selects one lawful leaf at a time;
- executes, proves, records, and persists evidence;
- performs bounded continuation search;
- continues to the next lawful leaf when lawful work remains.

A checkpoint, commit, proof pass, package, receipt, ledger update, or clean handoff state is a continuation point, not a stop point.

## Harness loop
Repeat:
1. inspect Git/repo state;
2. read live authority;
3. select the next lawful leaf;
4. read required files in full;
5. execute lawful bounded work;
6. run relevant proof;
7. record receipts, manifests, diffs, and ledger state where required;
8. perform bounded continuation search;
9. continue.

A response boundary is not an execution boundary. The user does not need routine progress updates.

## Stop rules
Stop only when one of these exact conditions is true:
1. observable context failure prevents coherent continuation;
2. hard runtime/tool failure prevents continuation after lawful recovery attempts;
3. explicit user stop, handoff, or output request exists;
4. explicit live authority forbids further execution;
5. bounded continuation search proves no lawful executable work remains.

Do not stop for checkpoint creation, package creation, proof pass, commit, receipt, ledger update, gate completion, tranche completion, branch creation, queue exhaustion, handoff preparation, a tidy response opportunity, or temporary inability to identify the next leaf.

## Continuation search
Failure to immediately identify the next executable leaf is not a stop condition. Before concluding that no lawful executable work remains, inspect at minimum:
- current `ROADMAP_LEDGER.md` state;
- active receipts and manifests;
- unresolved blockers;
- unresolved validation gaps;
- stale evidence risks;
- proof coverage gaps;
- authority inconsistencies;
- queue integrity state;
- manifest integrity state;
- current-pointer continuity;
- admissible audit, control, evidence, manifest, receipt, ledger, or planning-hardening leaves within the active authority class.

If a lawful executable leaf exists, select it, record the selection where required, and continue.

## Blocker rule
A blocker starts bounded resolution. It is not a stop condition.

When a selected leaf encounters a blocker:
1. read the nearest authority and affected files;
2. search the repo for relevant symbols, paths, configs, receipts, and tests;
3. determine the smallest lawful local resolution;
4. apply it only if the active authority permits it;
5. run targeted validation;
6. continue.

If unresolved, record it truthfully, mark affected claims `Unknown` or `blocked`, preserve evidence, and continue another lawful leaf where possible.

## Evidence and truthfulness
Do not claim `read`, `reviewed`, `verified`, `fixed`, `implemented`, `passed`, `complete`, `aligned`, `reconciled`, or `audited` unless direct evidence supports the claim.

Material claims require at least one of: paths, line ranges, command output, receipts, manifests, diffs, patches, artefacts, or official documentation. Otherwise label claims `Inferred`, `Unknown`, or `Unverified`.

Evidence must be reproducible, attributable, bounded, and inspectable.

## Read-before-mutate rule
Before substantive mutation, fully read:
- `AGENTS.md`;
- `PLANS.md`;
- `ROADMAP_LEDGER.md`;
- applicable route overrides;
- governing normative documents;
- governing execution plans or ledgers;
- all directly impacted files for the active leaf.

Do not replace required full reading with search, grep, AST parsing, embeddings, summaries, metadata, inventories, line counts, headings, filename inference, or partial sampling.

If full reading is infeasible, do not fabricate comprehension. Bound the unread material truthfully, avoid unlawful mutation based on unread material, and continue other lawful work where possible.

## FULL_READ_MANIFEST rule
Before substantive mutation, create or update the current `FULL_READ_MANIFEST` required by the active control surface.

For each required file, record path, reason for inclusion, read status, and mutation relevance.

Do not rely on stale manifests as current proof. Validate the explicit current-target manifest before closure claims. Manifest completion alone does not authorise stopping.

## Authority hierarchy
Authority order:
1. direct user instruction;
2. `AGENTS.md`;
3. `PLANS.md`;
4. `ROADMAP_LEDGER.md`;
5. governing normative documents;
6. route override files;
7. tests;
8. implementation code;
9. comments and docstrings.

Lower authority may not override higher authority. If authorities conflict, attempt lawful bounded resolution first. If unresolved, record the conflict precisely and continue other lawful work where possible.

## Governance order
Runtime behaviour must follow this order:
1. normative intent;
2. tests;
3. implementation;
4. documentation.

Tests govern runtime behaviour, but passing tests alone are not proof of correctness. Do not implement behaviour before governing intent and governing tests exist or are lawfully updated. False-positive resistance and evidence quality matter.

## Atlas governance
Atlas material is candidate intent only. Atlas content is non-authoritative until lawfully admitted.

Required migration order:
1. normative intent;
2. tests;
3. implementation;
4. evidence;
5. ledger update.

Do not directly mutate runtime behaviour from Atlas material outside lawful migration flow.

## Boundary discipline
Work one bounded leaf at a time. Do not silently broaden scope, batch unrelated authority classes, skip evidence recording, skip verification, or pivot authority surfaces without recording it.

Do not mutate runtime/source/tests/config/vocabulary/Atlas/generated slices unless live authority explicitly opens that boundary.

`_archive/*.tar.gz` remains excluded/skip-worktree unless explicitly routed into scope by live authority.

## Git discipline
Before mutation, confirm repository and branch state. Use isolated worker branches where practical.

Do not rewrite unrelated files, discard unrelated changes, or destroy audit history.

After mutation, preserve diffs or patches before closeout when feasible.

## Proof cadence
Before checkpoint, handoff, or closure claims, run the proof commands required by live authority.

At minimum, when available and relevant, run:
- `git status --short`;
- `git diff --check`;
- targeted tests for changed behaviour;
- current manifest validators;
- current registry or surface-record validators;
- active proof-block checks.

If validation cannot be run, state exactly why and run the next best local check.

## Packaging rule
Packaging preserves state; it does not authorise stopping. Creating tarballs, zips, checkpoints, bundles, manifests, receipts, commits, or proof logs does not end execution. After packaging, continue lawful work unless a stop rule is met.

## Closeout rule
A final response is allowed only when a stop rule is met.

If stopping because continuation became impossible, state the precise blocker, what was inspected, what changed, proof status, the next lawful gate or leaf, and where evidence is preserved.

Use `Known true`, `Ruled out`, and `Next gate` when useful for state compression.

## Response style
Be concise, evidence-backed, mechanically precise, and non-theatrical. Avoid fake certainty, aspirational completion language, ceremonial narration, and vague summaries where exact state is knowable.

The worker is not rewarded for stopping safely at checkpoints. The worker is rewarded for truthful continuity, bounded lawful progress, auditability, and persistence under uncertainty.

Before relying on a file, read it with enough care to avoid missing important details. For controlling authority and files materially governing the selected gate, full reading is required unless infeasible.

Search, grep, headings, manifests, JSON inspection, AST parsing, line counts, summaries, embeddings, schema extraction, or generated ledgers may assist discovery. They do not replace careful reading of important in-scope files.

For active-code Atlas content gates, each selected source/test/config/data/docstring file that contributes records is in scope and must be read before records are written from it. If a file is not read, the affected record must say `unread_material` in `blockers` and must not claim direct observation.

Do not claim a file was read, checked, reviewed, verified, fixed, implemented, passed, complete, or aligned unless the work was actually done and evidence is available.

## 7A. Mandatory FULL_READ_MANIFEST control

Before any surface record, test extension, source repair, receipt, proof-closure statement, or ledger update, the worker must write a `FULL_READ_MANIFEST` for the controlling files and selected material files.

Each manifest entry must include:

- `path`;
- `byte_count`;
- `line_count`;
- `sha256`;
- `read_method`;
- `full_read=true` or `full_read=false`;
- `chunk_ranges` when reading was chunked;
- `notes` only where needed.

Search, grep, AST extraction, generated inventories, summaries, and prior chat memory may assist discovery but cannot satisfy the full-read requirement. If full sequential reading cannot be proven for a selected leaf, the worker must record that leaf as blocked with exact unread/infeasible files and mark affected claims `Unknown`; during a user-authorised continue-until-tokens run, route to the next lawful control/audit/evidence/manifest/receipt/ledger hardening leaf rather than treating the single blocked leaf as a user-facing stop condition.

If a file is later used as evidence but is absent from `FULL_READ_MANIFEST`, the claim must be labelled `unread` or `inferred` and cannot support mutation, proof closure, or ledger closure. If a file changes after the manifest entry was created, the manifest entry is stale and must be regenerated before that file can be relied on.

Historical `FULL_READ_MANIFEST` files are point-in-time receipts only. They may prove what a prior worker claimed against that prior checkout state, but they must not be cited as current proof after the listed files change. Only a current, validator-passing manifest for the active target may support the active target's closure claim. The active target manifest must be regenerated after any mutation affecting a listed file. The manifest validator no-argument mode checks every retained manifest under `var/audit/active_code_atlas_001/full_read_manifests/`, including historical point-in-time manifests; use explicit current target manifest paths for current-pass closure proof unless the selected leaf is auditing the historical manifest universe itself. Do not include the validator's mutable side-effect output file `var/audit/active_code_atlas_001/reports/validate_full_read_manifest_output.json` in the same manifest being validated, because the validator rewrites that file during validation and would make the manifest stale by construction; treat it as side-effect proof output, not material input evidence for that manifest.

Workers are procedurally blocked from saying `read`, `checked`, `verified`, `complete`, or `closed` for a file-backed claim unless an auditable current-or-historical manifest entry supports the exact checkout state and files used for that claim.

The generated all-surface structural inventory remains navigation/scaffold only. It cannot satisfy or bypass a `FULL_READ_MANIFEST`.

## 8A. Execution cadence and no ordinary gate pauses

Passing a gate, proof block, targeted test, validation command, commit, package, or ledger update is a continuation point, not a user-facing stop point. A worker must continue to the next lawful target while current user authority and the live ledger still authorise the work.

Do not pause at ordinary gate boundaries merely to ask whether to proceed. During a user-authorised long run whose current instruction says to continue until tokens are exhausted, continue through the surface-by-surface workflow until context/token exhaustion, tool/runtime exhaustion, or an explicit user stop/report/handoff/package instruction prevents further lawful work in the current response.

Durability checkpoints and package smoke tests preserve work; they do not create an automatic recursive obligation to index/package the immediately previous package again. After recording useful checkpoint proof, continue to the next distinct lawful control/audit/evidence/manifest/receipt/ledger/planning-hardening leaf unless the user explicitly asks for recursive checkpoint indexing.

Diagnostic hygiene scans are discovery aids, not proof substitutes. To avoid recursive self-amplification, default live-control scans should target `AGENTS.md`, `PLANS.md`, `ROADMAP_LEDGER.md`, current receipts/reports/manifests, and selected small artefacts; exclude prior scan-output artefacts, including raw scan text, scan-classification reports/receipts, prior proof-output transcripts, large generated JSON, stdout captures, and historical pre-repair logs unless the selected leaf explicitly audits them. A prior proof-output transcript may record an expected point-in-time failure and must not be treated as live proof status when a later current manifest/report records validator-passing supersession. A prior scan-classification artefact may quote historical hits and must not be treated as a fresh live-control hit unless the selected leaf explicitly audits that artefact. Record any exclusion pattern in the scan report.

The following are bounded-leaf blockers, not user-facing stop conditions while other lawful control/audit work remains available:

1. a required controlling artefact or selected in-scope file is missing or unreadable;
2. active authorities contradict each other and the conflict cannot be resolved by the authority order in this plan;
3. proof or validation fails and the lawful repair path for that leaf is unclear or would cross a closed authority boundary;
4. the next attempted step would mutate a closed surface, including runtime trading behaviour, financial/risk authority, dependency files, original Atlas/Bridge JSON, generated Atlas slices, vocabulary data/admissions, or unapproved refactor work;
5. a bounded leaf or queue subset has been exhausted.

For each bounded-leaf blocker, record the blocker in the relevant receipt/ledger, mark affected claims `Unknown` or `blocked`, and select the next lawful control, audit, evidence, manifest, receipt, ledger, or planning-hardening leaf inside current authority. Gate reports remain required inside receipts, `ROADMAP_LEDGER.md`, commits, and final handoff evidence. They are not permission pauses.

Purpose: install this plan, seed the active-code Atlas schema draft from the observed Atlas/Bridge shape, and update the mutable ledger.

- Atlas/Bridge shape is ignored or replaced by an unrelated catalogue;

Allowed changes:

- `PLANS.md`;

### Gate 1 — Authority and schema lock

Purpose: freeze the active-code Atlas schema before content extraction.

Pass criterion:

- controlling authority files are read for the gate;
- Atlas intent shape and Bridge shape are recorded as schema inputs;
- eighteen architecture surfaces are copied from governing blueprint/current map evidence, not from memory;
- schema validation rules are written for required fields, enum fields, source path/line fields, and Bridge join fields;
- no active-code content records are generated yet except schema examples explicitly marked as examples.

Fail criterion:

- schema cannot preserve Atlas/Bridge comparability;
- schema permits records without evidence path and line range;
- schema collapses tests, code, and docstrings into one ambiguous truth field.

Allowed changes:

- active-code Atlas schema files;
- schema-lock receipt;
- ledger update.

### Gate 2 — Surface inventory and file selection

Purpose: select the active files to read for one architecture surface.

Pass criterion:

- exactly one architecture surface is selected unless user explicitly authorises a multi-surface pass;
- selected files are listed by path and reason;
- selected tests/proof blocks are listed separately from source/config/data/docstrings;
- unread files are not used for direct-observation records.

Fail criterion:

- files are selected only by name similarity without blueprint/current-map evidence;
- source and test truth are mixed;
- a runtime-sensitive or reserved surface is opened beyond read-only evidence extraction.

Allowed changes:

- surface inventory report;
- ledger and receipt updates.

No source or test changes.

### Gate 3 — Active evidence reading and record extraction

Purpose: create active-code Atlas records for the selected surface from read evidence.

Pass criterion:

- every record has source path and line range;
- runtime behaviour, tests, configs, receipts, data, schemas, and docstrings are recorded as separate evidence classes when they differ;
- docstring-only matches are labelled `docstring_only`;
- name matches alone are rejected;
- current-code output is not treated as normative truth.

Fail criterion:

- a record lacks evidence;
- a record asserts correctness without normative/test proof;
- a record imports Atlas donor language as active behaviour without active-code evidence.

Allowed changes:

- active-code Atlas records for the selected surface;
- extraction receipt;
- ledger update.

No source or test changes.

### Gate 4 — Active-code Atlas validation

Purpose: validate the active-code Atlas records for schema, evidence, joinability, and internal consistency.

Pass criterion:

- schema validation passes;
- required source path and line fields are present;
- record IDs are unique;
- architecture surface values match the governed eighteen-surface vocabulary or explicit `blocked_blueprint`;
- proof/docstring/code evidence classes remain separable.

Fail criterion:

- duplicate IDs exist;
- records cite missing paths without blockers;
- records claim implemented behaviour without code and proof evidence;
- records cannot join to Bridge/Atlas comparison fields.

Allowed changes:

- validation report;
- repair to active-code Atlas records only where evidence supports the repair;
- ledger and receipt updates.

### Gate 5 — Three-way comparison plan

Purpose: prepare the later comparison between Atlas intent, Atlas Bridge, and the active-code Atlas.

Pass criterion:

- comparison keys are defined;
- statuses are defined for `already_satisfied`, `partially_satisfied`, `missing`, `transform_required`, `blocked`, and `conflict`;
- future Tier A/B/C test work is queued from normative gaps, not current-code output;
- implementation/refactor remains closed.

Fail criterion:

- comparison treats donor Atlas as runtime authority;
- comparison treats active code as correctness oracle;
- test work is skipped before refactor.

Allowed changes:

- comparison plan/report;
- ledger and receipt updates.

No source or test implementation changes.

## One-gate-at-a-time law

Only one gate is active at a time.

Only one bounded objective is active inside that gate at a time.

A gate is closed only when the touched live control surfaces and required receipts agree on the same state.

## Document-touch law

Every active bounded pack must classify relevant surfaces as:

- touched
- read-only mandatory reading
- prohibited

A touched surface is editable.

A read-only mandatory-reading surface must be read and obeyed. It must not be edited unless the active bounded pack explicitly moves it into touched scope and states why.

A prohibited surface must neither be edited nor treated as mutable support for convenience changes.

No surface enters touched scope by assumption, adjacency, or convenience.

## State-integrity law

Any test, assertion, or control-surface rule that encodes a temporary or point-in-time state must declare its lifecycle as one of:

- later-state tolerant
- mandatory retire at closeout
- mandatory replace at closeout

A temporary-state surface must not remain in place as if it were permanent law after the state it described has lawfully changed.

## No-retroactive-scope-legalisation law

A file that was not in mutable scope at gate open must not be touched first and legalised later.

If an unlisted file becomes necessary during execution, stop and reopen the bounded pack before touching it.

## Adjacent-governed-surface law

If a gate touches a surface that belongs to a governed block, that governed block must be reconciled before closeout.

A green local slice does not close a gate while another touched governed block remains unreconciled.

## Receipt law

If branch truth changed, update every required receipt surface that records that changed truth.

Required receipt surfaces include:

- the active bounded pack surface when its truth changed
- `config/retained_test_registry.yaml` when test migration status changed
- touched manifest or proof-ownership surfaces when their truth changed
- touched control surfaces whose recorded state changed

A receipt is incorrect if it omits a changed live surface that current live doctrine requires it to record.

## Closeout law

A gate is not closed until all touched live control surfaces and required receipts agree on the same state.

If any touched live control surface or required receipt disagrees, the gate is not closed.

## Live-authority boundary law

The live authority stack is limited to the control documents and active bounded pack surfaces routed by current live doctrine.

Historical support material, retained evidence, and non-authority files do not enter the live authority stack unless a higher-priority live surface explicitly routes them there.

Repo-root `README.md` is not part of the live authority stack.

## Process-closeout rule

Work is not closed if any required process condition remains unmet.

That includes any case where:

- no active bounded pack is routed
- a touched governed surface remains unreconciled
- a required receipt is missing or incorrect
- current repo truth and stated repo truth do not match

A clean narrative does not close a gate.

# 08_TESTING_AND_PROMOTION_CORE

All repo paths in the numbered control stack are repo-root-relative.


## Scope of this document

This document owns:

- environment and install provenance for governed proof
- proof-tier law
- temporary-state proof lifecycle law
- vocabulary constraints inside proof artefacts
- checkpoint and docstring proof requirements where current live doctrine requires them
- documentation and control-surface proof law
- proof receipt law
- promotion and demotion law

## Environment and install provenance law

Governed proof must run in the repo-local declared environment.

That environment must be created from the repo packaging authority and the canonical install flow declared by current live doctrine.

If current live doctrine declares canonical setup commands such as `make install` or equivalent setup commands, those commands are the required environment path unless a higher-priority live surface explicitly routes a different path.

Ad hoc package installation, undeclared environment drift, or missing environment provenance makes governed proof insufficient.

## Proof-tier law

Governed proof is classified into three tiers:

- Tier A: blocking governed proof
- Tier B: bounded shadow proof
- Tier C: historical, observational, or non-blocking proof

A proof artefact is Tier A only when current live doctrine or the active bounded pack explicitly classifies that artefact as Tier A.

A proof artefact does not change tier by habit or convenience.

## Tier A law

Tier A owns the blocking proof required for the current claim.

If a Tier A artefact that owns a touched surface is red, missing, or unreconciled, the work is not ready for promotion.

A green local proof slice is insufficient while another Tier A artefact that owns a touched surface remains unreconciled.

## Tier B law

Tier B is lawful for bounded shadow checking that is relevant to the current tranche but that is not blocking by current live doctrine.

Tier B debt does not block promotion unless live doctrine or the active bounded pack explicitly promotes it to blocking status.

Tier B must not be presented as Tier A.

## Tier C law

Tier C contains historical, observational, predecessor, or cleanup proof that is not blocking for the current claim unless live doctrine or the active bounded pack explicitly promotes it.

Tier C must not remain treated as blocking after live doctrine and router truth move on.

## Existing Tier A fallout declaration law

If a gate changes a surface in a way that changes the live Tier A boundary for an existing block, the active bounded pack must declare the exact pre-existing Tier A proof files or families that are permitted to receive bounded fallout repair.

If no pre-existing Tier A fallout repair is authorised, the active bounded pack must say `none; stop and re-plan` before those files are touched.

## Packet-carriage proof law

If a tranche changes live packet-carriage law, packet-envelope law, or packet readers, Tier A proof must cover the changed packet families.

That proof must include:

- envelope conformance proof
- producer-side emission proof
- consumer-side acceptance proof
- preserved-seam distinction proof where packet carriage crosses bounded ownership surfaces
- invalid or degraded packet proof where the changed packet family lawfully emits those states

A packet-carriage tranche is incomplete if it proves only packet production or only packet consumption.

## Packet numeric-integrity proof law

If a tranche changes packet carriage for numeric fields, Tier A proof must include representative numeric-integrity cases for the changed packet family.

Those cases must cover the forms that matter for the changed contracts, including where applicable:

- signed values
- zero values
- decimal precision
- percentage scale
- magnitude-sensitive values where `0.01` and `0.0001` are not equivalent

A packet-carriage tranche is incomplete if numeric meaning drifts while envelope proof remains green.

## Packet state-semantics proof law

If a tranche changes packet carriage for a field whose state meaning depends on omission, `null`, or an explicit state value, Tier A proof must cover those distinctions for the changed packet family.

A packet-carriage tranche is incomplete if the migrated contract makes those states ambiguous.

## Install record law

Where governed proof is required, the execution record must make the environment path inspectable.

At minimum, the record must show the canonical setup command or commands that were used for the proof run.

If the environment path cannot be shown, the proof claim is incomplete.

## Temporary-state proof law

Any proof artefact that encodes a temporary or point-in-time state must declare its lifecycle as one of:

- later-state tolerant
- mandatory retire at closeout
- mandatory replace at closeout

A temporary-state proof artefact must not remain in place as if it were permanent law after the state it described has lawfully changed.

## Vocabulary-in-proof law

A non-admitted durable term must not enter a proof artefact that itself becomes lasting repo law.

That restriction applies to artefacts including:

- governed test names
- durable fixture names
- manifest labels
- proof-block names
- contract-facing assertions

Proof artefacts must not become a back door for vocabulary drift.

## Checkpoint proof requirement

If current live doctrine requires a checkpoint declaration for a changed proof artefact, that declaration is part of governed proof.

It must be explicit.

If a required checkpoint declaration is missing, the proof-backed claim is incomplete.

## Docstring proof requirement

If current live doctrine requires a docstring applicability declaration for a changed owned surface, that declaration is part of governed proof.

It must be explicit.

If a required docstring declaration is missing, the proof-backed claim is incomplete.

## Documentation and control-surface proof law

Documentation, router, manifest, retained-test-registry, and control-surface changes are not exempt from governed proof.

If current live doctrine requires those changes to be proven through a governed proof artefact, that proof must run and be recorded before the changed repo truth is claimed.

Documentation work is not self-validating merely because it does not change runtime code.

## Proof receipt law

If proof-backed branch truth changed, update every required proof receipt surface that records that changed truth.

Required proof receipt surfaces include:

- touched proof-manifest or proof-block ownership surfaces when their truth changed
- `config/retained_test_registry.yaml` when tier status changed
- touched control-surface receipts affected by the changed truth

A proof-backed claim is incomplete if a required proof receipt is missing or if it records the wrong state.

## Promotion and demotion law

A proof artefact moves from Tier B or Tier C to Tier A only by explicit live doctrine or lawful active-pack authority.

A proof artefact moves from Tier A only by explicit live doctrine or lawful active-pack authority together with truthful manifest and receipt reconciliation.

Silent promotion and silent demotion are prohibited.

## Proof-closeout rule

Proof-backed work is not ready for promotion if any required proof condition remains unmet.

That includes any case where:

- required blocking proof is red, missing, or unreconciled
- the environment provenance is missing or unlawful
- a temporary-state proof artefact has no declared lifecycle
- a required checkpoint declaration is missing
- a required docstring declaration is missing
- a required proof receipt is missing or incorrect

A persuasive narrative does not make insufficient proof sufficient.

## 0. Core law

The native NVDA codebase must be structured as a clean target-state codebase.

All production code, tests, contracts, repositories, adapters, schemas, services, configuration surfaces, and migration work must conform to the target architecture defined by this document.

Current-state mess does not define future structure. Legacy convenience does not define target ownership. Migration pressure does not justify blurred package placement, hidden coupling, mixed responsibilities, or unclear seams.

A code change is not architecturally valid unless the affected capability can be assigned to:

1. a target package or subpackage;
2. a target module or component form;
3. an owning authority;
4. a lawful seam and carrier, where a boundary is crossed;
5. a persistence owner, where state is stored or read;
6. a test family, where behaviour or structure requires proof;
7. a traceability path, where migration or current-state carry-forward is involved;
8. an honest structural status: `Locked`, `Provisional`, or `Reserved`;
9. an honest implementation-truth status: `implemented`, `thin_seam`, `placeholder`, `reserved`, `future_only`, `legacy_only`, or `rejected`.

This document is the target architecture benchmark for the native deterministic NVDA repo.

## 3. Status models

This document uses two separate status models. They must not be conflated.

### 3.1 Structural status

Every target architecture item uses one of three structural status values.

| Status | Meaning | Rule |
|---|---|---|
| `Locked` | The benchmark shape is fixed now. | Code must conform to it. |
| `Provisional` | The likely target shape is known, but final details are not fixed. | Code may proceed only within the stated bounded shape. |
| `Reserved` | The target role is known, but the final allocation is unresolved. | Code must not guess or hard-code the unresolved allocation. |

A structural status value is not a progress label.

`Reserved` is not a defect. Hidden ambiguity is a defect.

### 3.2 Implementation-truth status

Every sequential architecture surface must carry exactly one implementation-truth status.

| Status | Meaning | Rule |
|---|---|---|
| `implemented` | Native code and proof surfaces currently satisfy the surface. | The claim must cite native code and proof evidence. |
| `thin_seam` | A lawful native seam exists, but behaviour is incomplete. | The surface must not be described as mature implemented behaviour. |
| `placeholder` | A named native shell exists with little or no behaviour. | The surface must not be treated as behaviourally complete. |
| `reserved` | Architecture reserves the surface, and native implementation is not present. | Later admissibility work is required before implementation. |
| `future_only` | Planned future surface with no current native implementation. | It must not be used as current runtime truth. |
| `legacy_only` | Found only in legacy or Atlas evidence. | It must not become native architecture without later admissibility work. |
| `rejected` | Not part of native architecture. | The reason for rejection must be stated. |

A surface marked `implemented` must cite native code and proof evidence.

A surface marked `thin_seam`, `placeholder`, `reserved`, or `future_only` must not be described as completed runtime behaviour.

Durable architecture terms used by this document must be governed by `docs/10_VOCABULARY_AND_TERM_GOVERNANCE_CORE.md` before freeze. A target term that is not governed, admitted, aliased, or explicitly quarantined by the vocabulary process is not accepted normative language.

## 6. Target Structure law

Target Structure governs package and subpackage placement.

Each target package or subpackage must have:

1. one bounded responsibility;
2. allowed contents;
3. forbidden contents;
4. preferred component forms;
5. an honest structural status.

Code must be placed by target responsibility, not by historical file location, local convenience, or similarity of names.

A package must not become a dumping ground for unrelated services, schemas, adapters, repositories, orchestration, tests, and configuration.

A subpackage must not own behaviour that belongs to another layer simply because the dependency is nearby.

If a capability does not have a lawful package home, the capability is `Reserved` until the target home is resolved.

## 7. Component Skeleton law

Component Skeleton governs the internal shape of modules.

Every module must have a coherent primary responsibility.

A component must use the correct form for its job:

| Component form | Owns | Must not own |
|---|---|---|
| Adapter | External boundary translation. | Core domain decisions. |
| Contract | Data shape crossing a boundary. | Runtime behaviour. |
| Schema or model | Validated data structure. | Service orchestration. |
| Service | Runtime operation or domain action. | Persistence authority unless explicitly assigned. |
| Repository or store | Durable state read/write boundary. | Candidate formation or strategy logic. |
| Orchestrator | Ordered coordination. | Hidden business rules outside authorised stages. |
| Configuration authority | Governed parameters and allowed values. | Ad hoc runtime mutation. |
| Test surface | Proof of structure or behaviour. | Production decision logic. |

A module must not mix component forms unless the target architecture explicitly allows that mixture.

Helper functions do not define ownership. Ownership is defined by bounded responsibility and target component form.

---

## 8. Ownership Matrix law

Ownership Matrix governs capability ownership.

Every major capability or concept must have:

1. a target owner;
2. a target module or area;
3. a preferred form;
4. an input carrier, where applicable;
5. an output carrier, where applicable;
6. forbidden placement;
7. an honest status.

A capability must not be implemented in two places with competing authority.

A capability must not be placed in an adapter, schema, repository, or test merely because that location is convenient.

A capability must not be carried forward from legacy code until its target owner is known or explicitly reserved.

Where ownership is unresolved, the correct action is `Reserved`, not implicit implementation.

---

## 9. Seam Contract law

Seam Contracts govern boundaries between architecture surfaces.

A seam must define:

1. upstream owner;
2. downstream owner;
3. carrier type;
4. required invariants;
5. persistence side effects;
6. allowed variants;
7. forbidden variants;
8. carrier family;
9. seam category;
10. traceability reference, where migration is involved.

A boundary crossing must use an explicit carrier or contract.

Data must not cross architecture boundaries through hidden imports, shared mutable objects, implicit globals, undocumented dictionaries, or test-only shortcuts.

A seam must not become an owner of the decisions it transports.

A carrier must not become business logic.

A downstream surface must not read upstream internals if the seam defines a lawful carrier.

---

## 10. Bridge and Shell Policy law

Bridge and Shell Policy governs transitional, advisory, optional, and shell surfaces.

A partial surface is lawful only when it is explicitly labelled and bounded.

A bridge or shell must define:

1. target home;
2. allowed behaviour;
3. required label;
4. forbidden behaviour;
5. target resolution path;
6. honest status.

A shell must not masquerade as completed behaviour.

A bridge must not become permanent architecture by inertia.

An advisory surface must not make binding runtime decisions unless the target architecture assigns that authority.

A transitional surface must have a resolution path or a reservation.

---

## 11. Persistence Architecture law

Persistence Architecture governs durable state.

Every persistence domain must define:

1. authoritative writer;
2. primary readers;
3. persistence class;
4. bootstrap or fallback rule;
5. forbidden mixing;
6. target repository or store module;
7. traceability reference, where migration is involved.

Only the authoritative writer may write durable truth for a persistence domain.

Readers must consume through lawful repository, store, contract, or query surfaces.

Persistence must not be mixed with candidate formation, orchestration, adapter translation, schema validation, or tests unless explicitly assigned.

State must not be duplicated into competing durable stores without a governed reconciliation rule.

A bootstrap or fallback path must not silently become normal runtime authority.

---

## 12. Test Architecture law

Test Architecture governs proof families, not individual test-case trivia.

Every benchmark family must map to a required test family.

A test family must define:

1. primary scope;
2. target subsystem;
3. failure signal;
4. notes or constraints;
5. honest status.

Tests must prove the architecture claim they are attached to.

A green test does not make code architecturally valid if the code is in the wrong package, wrong module form, wrong ownership boundary, wrong seam, or wrong persistence domain.

A test must not encode a messy current-state compromise as future architecture truth.

Where code structure is governed, tests must verify the boundary that matters, not merely execute the path.

---

## 13. Reservations and Provisional Allocations law

Reservations govern bounded open questions.

A reservation must define:

1. the open allocation point;
2. why it is not locked yet;
3. bounded options;
4. evidence required to resolve it;
5. current benchmark constraint;
6. owner to decide later;
7. likely target home, where known;
8. traceability reference, where migration is involved.

Unresolved architecture must be visible.

A reserved item must not be implemented as though it were locked.

A provisional item must not expand beyond its bounded options.

A developer must not create a new target home to avoid resolving a reservation.

---

## 14. Module Allocation Appendix law

Module allocation is migration-facing detail.

It assists current-state and donor material in finding target homes.

It must not override Target Structure, Component Skeleton, Ownership Matrix, Seam Contracts, Persistence Architecture, Test Architecture, or Reservations.

A module allocation entry must define:

1. target package;
2. target subpackage;
3. target module;
4. bounded responsibility;
5. preferred form;
6. primary inputs;
7. primary outputs;
8. forbidden co-location;
9. observed current basis, where relevant.

A current file must not be moved or rewritten directly into the native repo unless its target allocation is lawful.

Observed current basis explains what exists. It does not authorise preserving messy structure.

---

## 15. Traceability Appendix law

Traceability is migration evidence.

It explains why current-state or donor material was carried forward.

It must not pollute canonical target architecture.

A traceability entry must define:

1. traceability reference;
2. target surface;
3. donor or current-state source;
4. observed current basis;
5. reason carried forward.

Traceability must not become implementation authority.

A traceability reference is valid only when it leads to a lawful target package, component form, owner, seam, persistence owner, and test family.

---

## 16. Anti-mess law

The following patterns are prohibited:

1. mixed-responsibility modules;
2. business logic inside adapters;
3. orchestration hidden inside schemas or contracts;
4. persistence writes from non-authoritative surfaces;
5. shared mutable state across architecture boundaries;
6. implicit carriers where a seam requires a contract;
7. duplicate owners for the same capability;
8. test fixtures that become runtime authority;
9. migration code that bypasses target ownership;
10. reserved decisions implemented as if locked;
11. provisional decisions expanded beyond their bounded shape;
12. bridge or shell surfaces presented as completed behaviour;
13. code placement based on legacy file location rather than target architecture;
14. current-state compromise treated as native design.

A patch containing any prohibited pattern fails architecture review.

---

## 17. Acceptance rule for code changes

A code change is architecturally acceptable only when the reviewer can answer the following questions without guessing.

| Question | Required answer |
|---|---|
| Where does this belong? | Target package, subpackage, and module. |
| What form is it? | Adapter, contract, schema, service, repository, orchestrator, configuration authority, or test surface. |
| Who owns it? | One target owner. |
| What may it consume? | Lawful inputs or carriers. |
| What may it emit? | Lawful outputs or carriers. |
| What boundary does it cross? | Explicit seam contract, or no boundary crossing. |
| Does it persist state? | Authoritative writer and primary readers, or no persistence. |
| What proves it? | Required test family and failure signal. |
| Is anything unresolved? | `Reserved` or `Provisional` with bounded options. |
| Is any current-state mess being preserved? | No. |

If any answer is missing, the change is incomplete.

If any answer depends on undocumented inference, the change is incomplete.

If any answer contradicts a locked target structure, the change is rejected.
