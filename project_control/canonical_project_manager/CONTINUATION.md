## 3. Feature modularity and architectural modularity

The project must preserve both forms of modularity, and must not confuse them.

**Feature modularity** is the ability to add, remove, alter or extend a
user-facing capability without redesigning unrelated capabilities. It is a
product result: a calendar feature, replay view or risk observation can evolve
as one bounded concept.

**Architectural modularity** is the mechanism that makes that result true. It
requires one semantic owner, a typed public seam, inward dependency direction,
explicit identity/time/state ownership, substitutable external ports, bounded
side effects, compatibility adapters that do not own meaning, and proof that
can exercise the module without booting or mutating unrelated parts of the
system.

Feature flags, route separation, package names or separate test folders do not
provide feature modularity when hidden state, private imports, fabricated
identity or shared mutable contracts still couple the implementation. Equally,
architectural purity is not an end in itself: do not create services, plugin
frameworks, abstraction layers or package moves unless they protect a real
owner boundary or the next bounded concept.

## 5. Compatibility and migration rule

Physical coexistence between canonical `mXX` packages and older package paths is
acceptable only as controlled compatibility:

1. all new product meaning is defined and implemented at the accepted owner;
2. the owner's public seam is the only canonical entry;
3. a retained older path may translate inward, project outward or preserve a
   stable import, but may not create identity, policy, state or domain meaning;
4. canonical modules must not call outward into a compatibility path to obtain
   private truth;
5. a touched compatibility path must be proved behaviourally subordinate to
   the owner, or be quarantined from canonical M00 composition;
6. broad physical relocation is demand-driven, not a precondition to resume
   feature work.

This rule permits practical progress without allowing two architectures to
coexist as equal authorities.

## 6. Standard for a dependable module foundation

Before a module is used as the owner or dependency foundation for a new
concept, its existing module record must contain a current pass against the
following eight questions. This is an evidence decision inside the existing
gates, not a new gate or a replacement status vocabulary.

1. **Authority:** the current proposition, owner, exclusions and any Atlas or
   decision lineage are unambiguous and agree with the numbered doctrine.
2. **Public seam:** canonical inputs and outputs are typed, immutable where
   authority requires it, importable from one owner surface, and independently
   constructible in a hermetic test.
3. **Dependency direction:** direct and transitive imports in the affected cone
   follow the accepted graph; compatibility and transaction/evidence ports are
   explicit; no unresolved private dependency is hidden by re-export.
4. **Identity, time and state:** IDs, timestamps, clocks, policy versions,
   repositories and mutable state have one owner and are injected or issued by
   that owner. No canonical path fabricates authority or leaks process-global
   mutation between tests or runs.
5. **Proof admission:** every retained physical test file relevant to the
   module and affected dependency cone has an exact registry/proof disposition;
   there are no stale paths or unowned proof nodes.
6. **Public-seam proof:** focused proof covers a conforming case, the material
   prohibited or missing case, and a plausible false-positive implementation;
   state isolation, order, replay, restart or port substitution is covered when
   the module owns it.
7. **Current validation:** focused and affected proof is green; relevant
   physical partitions are green after semantic adjudication; architecture,
   import, vocabulary, state and replay checks pass where applicable; there are
   no new failures in the current aggregate route.
8. **Limits and compatibility:** alpha limitations, external unknowns,
   compatibility surfaces and any time-bounded exception are explicit, have an
   owner, and cannot be mistaken for production or live readiness.

Reuse accepted module evidence wherever its proposition, seam and environment
remain comparable. Read and rerun only the delta needed to make the current
decision. Do not require a new dossier, archive or independent reviewer for
each module. Independent challenge remains risk-triggered under the existing
Gate C protocol.

- retain the proposition and repair the owner through the existing gates;

  proof-control claim.

Do not repair by count, blanket expected-failure markers, skips, assertion
weakening, compatibility aliases that create a second owner, or wholesale
donor patches. One semantic cause may close many nodes; one node may still

## 11. Standard route for every future concept

One bounded concept proceeds through the following exact flow:

### Definition

Record the user outcome, owner module, public seam, in-scope and excluded
behaviour, dependency cone, state/identity/time effects, compatibility impact,
Atlas/decision lineage where relevant, vocabulary impact, proof proposition and
risk class. If more than one semantic owner is required, split the concept or
name one composition change and its separately owned prerequisites.

### Governing alignment

Read the owner core/working documents and affected boundary law. Amend only the
smallest existing normative surface needed for new meaning. Do not rewrite
accepted architecture or create a new methodology for an ordinary feature.

### Tests

Admit the exact physical test path and proof block in the same concept. Write
the smallest public-seam proof that covers the positive result, the material
fail-closed/prohibited result and a plausible false positive. Expected red must
fail for the intended missing behaviour.

### Implementation

Implement the smallest owner-local change after Gate D opens. New meaning lands
behind the owner public API. Compatibility adapters may translate inward but
receive no new authority. External effects use injected ports; state mutation
uses the owning module and M13 mechanics where applicable.

### Validation

Run focused and affected proof, relevant physical partitions, the admitted
aggregate route, and architecture/vocabulary/state/replay checks triggered by
the change. At the concept integration checkpoint run the full retained
physical Tier A/Tier B route once. Keep a concise reproducible summary and
failing-node delta; do not retain duplicate successful transcripts.

### Gated integration

Update the existing module record and roadmap, verify exact proof admission and
clean Git state, then integrate one approved semantic slice. Shared-surface
changes integrate serially. The next concept begins from that checkpoint, not
from an unaccepted parallel branch.

This route supports addition, removal and replacement of product capabilities
without hidden change elsewhere because each concept is bound to one owner,
one public seam, one explicit dependency cone and one current verification
surface.

## 12. Stop conditions and exclusions

Stop and reopen the bounded unit when authority is contradictory, the owner or
dependency direction is unresolved, a supposedly local change requires a new
shared semantic owner, a retained test cannot be lawfully adjudicated, or a
required environment/source is unavailable. Escalate to the user only when the
choice introduces new product meaning, external authority, destructive action
or scope outside this strategy.

The original strategy assignment did not authorise production mutation. The
current execution instruction authorises only the bounded repairs admitted by
this programme and its existing gates. Donor implementation integration, live
credentials or network execution, production claims, a microservice/plugin
conversion, wholesale legacy package relocation, broad Atlas re-adjudication
and a new retrospective programme remain excluded.
