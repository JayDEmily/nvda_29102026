This document is the canonical account of the next programme stage. It was
authorised to resolve the present-state and continuation question after the
comparative worker audit. It governs current status, the bounded foundation
readiness programme, the standard for using a module as a development
foundation, and the route back to ordinary feature delivery.

It does not replace the numbered normative stack, the accepted M00–M15
allocation, the existing `C-NORM → C-PROOF → Gate D` method, or accepted module
evidence. Where an older plan, closeout, roadmap paragraph or working-document
implementation snapshot says that repository debt is wholly retired, that M03
is the current delivery unit, or that a closed subordinate pack is active, this
document and the live roadmap supply the later present-tense correction. The
older record remains historical evidence; its accepted semantic law is not
silently revoked.

## 1. Canonical decision

1. The primary repository is the sole continuation base. Do not merge the
   secondary repository, transplant its control state, or use its test counts as
   proof of the primary repository.
2. The alpha is not restarted. Accepted M00–M13 behaviours, M13 state work,
   M00 transport routing, owner-fact completion, bounded SQLite persistence,
   fail-closed operational adapters, Tier C specimens and vocabulary
   reconciliation remain the foundation of the continuation.
3. Historical Gate D acceptance remains valid for the behaviour and checkpoint
   it actually proved. It is not, by itself, a claim that every current physical
   test is admitted or that the later aggregate repository is ready for
   unrestricted extension.
4. One bounded foundation-readiness programme must reconcile that later
   aggregate state. It must work by common cause and module boundary, not by
   replaying the alpha module programme or repairing 247 test nodes one at a
   time.
5. Normal planned feature development resumes immediately after the readiness
   checkpoint in section 10. No further general retrospective or new assurance
   methodology is required at that point.

## 3. Feature modularity and architectural modularity

The project must preserve both forms of modularity, and must not confuse them.

**Feature modularity** is the ability to add, remove, alter or extend a
user-facing capability without redesigning unrelated capabilities. It is a
product result: a calendar feature, replay view or risk observation can evolve
as one bounded concept.

**Architectural modularity** is the mechanism that makes that result true. It
requires one semantic owner, a typed public seam, inward dependency direction,
explicit identity/time/state ownership, substitutable external ports, bounded
side effects, compatibility adapters that do not own meaning, and proof that
can exercise the module without booting or mutating unrelated parts of the
system.

Feature flags, route separation, package names or separate test folders do not
provide feature modularity when hidden state, private imports, fabricated
identity or shared mutable contracts still couple the implementation. Equally,
architectural purity is not an end in itself: do not create services, plugin
frameworks, abstraction layers or package moves unless they protect a real
owner boundary or the next bounded concept.

M01–M12 as semantic owners, M13 as transaction/storage mechanism and M14/M15 as
governance planes.

| M02 | financial-calendar reference, policy, snapshot and projection |
| M03 | prepared truth, field resolution, limitations and prepared lineage |

| M13 | transaction, idempotency, atomic receipt and storage mechanisms without domain ownership |

The accepted runtime dependency graph remains binding. Cross-module use must
enter through an owning module's public export or an explicitly accepted
evidence/transaction port. New imports of another module's private submodule are
prohibited. Existing private or compatibility imports must be inventoried when
their dependency cone is touched; a confirmed forbidden edge must be removed or
replaced before that cone is used for new development.

M04 may remain a logical module whose current implementation allocation spans
the governed packet paths. Creating a cosmetic `m04` package is not a readiness
prerequisite. If the next M04 concept would broaden a shared legacy packet file,
that concept must first establish an explicit M04 public package boundary or
otherwise demonstrate equally clear owner isolation.

M13 supplies transaction and persistence mechanics; it never becomes owner of
capital, execution, portfolio or replay meaning. External market-data, broker
and durable-store implementations remain injected ports. Offline and fail
closed remain the defaults.

## 5. Compatibility and migration rule

Physical coexistence between canonical `mXX` packages and older package paths is
acceptable only as controlled compatibility:

1. all new product meaning is defined and implemented at the accepted owner;
2. the owner's public seam is the only canonical entry;
3. a retained older path may translate inward, project outward or preserve a
   stable import, but may not create identity, policy, state or domain meaning;
4. canonical modules must not call outward into a compatibility path to obtain
   private truth;
5. a touched compatibility path must be proved behaviourally subordinate to
   the owner, or be quarantined from canonical M00 composition;
6. broad physical relocation is demand-driven, not a precondition to resume
   feature work.

This rule permits practical progress without allowing two architectures to
coexist as equal authorities.

## 6. Standard for a dependable module foundation

Before a module is used as the owner or dependency foundation for a new
concept, its existing module record must contain a current pass against the
following eight questions. This is an evidence decision inside the existing
gates, not a new gate or a replacement status vocabulary.

1. **Authority:** the current proposition, owner, exclusions and any Atlas or
   decision lineage are unambiguous and agree with the numbered doctrine.
2. **Public seam:** canonical inputs and outputs are typed, immutable where
   authority requires it, importable from one owner surface, and independently
   constructible in a hermetic test.
3. **Dependency direction:** direct and transitive imports in the affected cone
   follow the accepted graph; compatibility and transaction/evidence ports are
   explicit; no unresolved private dependency is hidden by re-export.
4. **Identity, time and state:** IDs, timestamps, clocks, policy versions,
   repositories and mutable state have one owner and are injected or issued by
   that owner. No canonical path fabricates authority or leaks process-global
   mutation between tests or runs.
5. **Proof admission:** every retained physical test file relevant to the
   module and affected dependency cone has an exact registry/proof disposition;
   there are no stale paths or unowned proof nodes.
6. **Public-seam proof:** focused proof covers a conforming case, the material
   prohibited or missing case, and a plausible false-positive implementation;
   state isolation, order, replay, restart or port substitution is covered when
   the module owns it.
7. **Current validation:** focused and affected proof is green; relevant
   physical partitions are green after semantic adjudication; architecture,
   import, vocabulary, state and replay checks pass where applicable; there are
   no new failures in the current aggregate route.
8. **Limits and compatibility:** alpha limitations, external unknowns,
   compatibility surfaces and any time-bounded exception are explicit, have an
   owner, and cannot be mistaken for production or live readiness.

Reuse accepted module evidence wherever its proposition, seam and environment
remain comparable. Read and rerun only the delta needed to make the current
decision. Do not require a new dossier, archive or independent reviewer for
each module. Independent challenge remains risk-triggered under the existing
Gate C protocol.

## 8. Bounded foundation-readiness programme

The later execution worker must open one subordinate plan under this ExecPlan.
Its only objective is to establish the readiness checkpoint in section 10. It
must use the following order, one semantically complete unit at a time.

### 8.1 Exact proof universe and baseline truth

- reproduce the current physical Tier A/Tier B inventory and exact
  registry/proof join on the continuation checkpoint;
- adjudicate the 32 unadmitted files as retain and admit, merge into an owning
  proof family, or retire as superseded/non-authoritative;
- resolve duplicate/stale control rows only where the exact join proves a real
  ambiguity;
- preserve failing-node identity and cluster failures by shared proposition or
  traceback cause before any implementation repair.

This unit changes proof/control surfaces only. It must not infer that a physical
test is authoritative merely because it exists, nor hide a retained red test.

### 8.2 Prepared identity and packet boundary

Close the M03 prepared-context-to-M04 packet identity mismatch as one boundary
unit. The unit must prove caller-owned producer/run/trace/scenario/time identity,
complete owner validation, correct source/derived lineage, degraded limitation
handling and fail-closed missing identity through the public seam. It must then
run the packet, runtime, upstream-cognition and M00 affected cones.

### 8.3 Typed ingress and canonical composition boundary

Replace the untyped M01 request payload with one concrete repository-owned
typed ingress contract and adapt the current M00/transport caller cone in the
same semantic unit. API or legacy routes must either translate into explicit
M00/M01 inputs or remain demonstrably noncanonical and unselected. No boundary
may fabricate missing source, packet, run, trace, scenario, policy or time
identity.

### 8.4 Dependency, state and vocabulary integrity

Close the remaining high-confidence structural findings as narrow units:

- move or duplicate the semantic fingerprint primitive into a lawful neutral or
  owner-local surface and remove the forbidden M12-to-M10 dependency;
- freeze governed process-wide policy values without making legitimate
  per-instance state unmodifiable;
- exclude owned projection headers from vocabulary candidate observation while
  preserving detection of real unadmitted names;
- adjudicate compatibility API process-local state by routing it to an owner,
  isolating it per injected instance, or proving it is unreachable from
  canonical M00.

These units may be reordered only when their read/write sets are disjoint and
the Project Manager records the dependency reason. Canonical integration
remains serial.

### 8.5 Residual physical failure families

Rerun the affected partitions after the common causes close. For each remaining
failure family, compare the assertion with current normative authority and use
one of three lawful dispositions:

- retain the proposition and repair the owner through the existing gates;
- retain the proposition but rewrite a stale test so it exercises the current
  public seam without weakening the meaning; or
- retire the test because its proposition is explicitly superseded,
  noncanonical or duplicated, recording the governing locator and removing its
  proof-control claim.

Do not repair by count, blanket expected-failure markers, skips, assertion
weakening, compatibility aliases that create a second owner, or wholesale
donor patches. One semantic cause may close many nodes; one node may still
justify a stop if it exposes contradictory authority.

### 8.6 Readiness closure

Run the section 10 matrix once on the exact final checkpoint, update existing
module records and the live roadmap, and retain one concise validation summary.
Do not generate a second retrospective dossier or repeat unchanged module
histories.

## 9. Existing gates during continuation

Every repair that changes behaviour still follows the existing sequence:

`C-NORM normative alignment → C-PROOF truthful public-seam proof → Gate D bounded implementation`

Proof/admission corrections with no production behaviour use the applicable
M14 control route and still require an authority locator and falsifiable check.
The foundation record in section 6 is completed after affected Gate D
validation; it does not delay implementation with a fourth gate.

Module-local progress remains allowed inside the readiness programme. A unit
does not wait for unrelated modules, and it need not repeat a previously
accepted proposition when the current failure is only at a known boundary.
Shared packet, proof, vocabulary, composition and configuration surfaces are
serial integration points. Independent validation remains mandatory only for
the high-consequence boundaries already named in the Gate C protocol.

## 10. Point at which normal feature development resumes

Publish one exact continuation-readiness checkpoint when all of the following
are true on the same commit and declared environment:

1. the current retained physical Tier A and Tier B test universes have zero
   failures, errors and skips after semantic adjudication;
2. every retained physical test file is exactly admitted, with zero stale and
   zero unadmitted paths; a retired test is absent from both the physical tree
   and active proof control;
3. the curated `alpha_current` route is green and contains no test outside the
   declared physical/admission inventory;
4. the exact module graph has no cycles, syntax errors or unresolved imports,
   and canonical cross-module edges conform to the accepted dependency graph or
   an explicit bounded compatibility/evidence/transaction exception;
5. fresh-import order, state isolation, replay serialisation and forged-boundary
   probes are green on the current module set;
6. governed policy values are caller-immutable, the vocabulary scan is clean
   under current exact dispositions, and scanner-owned metadata does not create
   candidates;
7. prepared packet identity, typed M01 ingress, M12 dependency direction and
   canonical M00 identity/state boundaries are closed or explicitly quarantined
   with proof that canonical composition cannot reach the compatibility path;
8. the ExecPlan, roadmap, module records, proof controls, validation summary,
   Git branch and commit all describe the same current state.

This checkpoint is alpha continuation readiness only. It does not establish
live trading, production durability, operational commissioning, profitability
or production replay.

Once the checkpoint is published, normal incremental feature development may
resume immediately. No further repository-wide assurance programme is a
prerequisite unless later evidence invalidates the baseline.

## 11. Standard route for every future concept

One bounded concept proceeds through the following exact flow:

### Definition

Record the user outcome, owner module, public seam, in-scope and excluded
behaviour, dependency cone, state/identity/time effects, compatibility impact,
Atlas/decision lineage where relevant, vocabulary impact, proof proposition and
risk class. If more than one semantic owner is required, split the concept or
name one composition change and its separately owned prerequisites.

### Governing alignment

Read the owner core/working documents and affected boundary law. Amend only the
smallest existing normative surface needed for new meaning. Do not rewrite
accepted architecture or create a new methodology for an ordinary feature.

### Tests

Admit the exact physical test path and proof block in the same concept. Write
the smallest public-seam proof that covers the positive result, the material
fail-closed/prohibited result and a plausible false positive. Expected red must
fail for the intended missing behaviour.

### Implementation

Implement the smallest owner-local change after Gate D opens. New meaning lands
behind the owner public API. Compatibility adapters may translate inward but
receive no new authority. External effects use injected ports; state mutation
uses the owning module and M13 mechanics where applicable.

### Validation

Run focused and affected proof, relevant physical partitions, the admitted
aggregate route, and architecture/vocabulary/state/replay checks triggered by
the change. At the concept integration checkpoint run the full retained
physical Tier A/Tier B route once. Keep a concise reproducible summary and
failing-node delta; do not retain duplicate successful transcripts.

### Gated integration

Update the existing module record and roadmap, verify exact proof admission and
clean Git state, then integrate one approved semantic slice. Shared-surface
changes integrate serially. The next concept begins from that checkpoint, not
from an unaccepted parallel branch.

This route supports addition, removal and replacement of product capabilities
without hidden change elsewhere because each concept is bound to one owner,
one public seam, one explicit dependency cone and one current verification
surface.

## 12. Stop conditions and exclusions

Stop and reopen the bounded unit when authority is contradictory, the owner or
dependency direction is unresolved, a supposedly local change requires a new
shared semantic owner, a retained test cannot be lawfully adjudicated, or a
required environment/source is unavailable. Escalate to the user only when the
choice introduces new product meaning, external authority, destructive action
or scope outside this strategy.

The continuation does not authorise production code in this strategy task,
donor implementation integration, live credentials or network execution,
production claims, a microservice/plugin conversion, wholesale legacy package
relocation, broad Atlas re-adjudication, or a new retrospective programme.
